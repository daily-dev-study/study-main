# 메모리 계층 구조와 캐시 메모리 (Memory Hierarchy & Cache)

## 1. 면접 핵심 Q&A

### Q1. 메모리 계층 구조는 왜 필요한가요?

빠른 메모리는 비싸고 대용량으로 만들기 어렵습니다. 그래서 **작고 빠른 캐시 + 크고 저렴한 RAM**을 함께 사용해, 비용과 용량을 확보하면서 평균 접근 시간을 줄입니다.

### Q2. 시간 지역성과 공간 지역성은 어떻게 다른가요?

| 구분 | 의미 | 예시 |
|---|---|---|
| **시간 지역성** | 방금 쓴 것을 곧 다시 사용 | 짧은 루프의 명령어를 반복 실행 |
| **공간 지역성** | 방금 쓴 주소 주변을 곧 사용 | 배열을 앞에서부터 순회 |

캐시는 데이터를 **남겨 두어** 시간 지역성을, 주변 데이터를 **함께 가져와** 공간 지역성을 활용합니다.

### Q3. 캐시 라인이 무엇인가요?

캐시가 데이터를 보관하고 주고받는 **덩어리 단위**입니다. 많은 CPU에서 64바이트를 사용합니다.

4바이트 정수라면 한 라인에 16개 분량이 들어갑니다. 배열을 순서대로 읽으면 함께 가져온 주변 원소를 재사용할 수 있습니다.

> 라인 크기는 CPU마다 다르며, 첫 라인에 들어가는 배열 원소 수는 시작 주소의 정렬에 따라 달라집니다.

### Q4. 캐시 미스가 나면 바로 RAM에 가나요?

**L1에 없어도 L2나 L3에서 찾을 수 있습니다.** 다른 코어의 캐시에서 받을 수도 있습니다.

해당 데이터가 필요한 명령어는 기다리지만, CPU는 실행 가능한 다른 명령어로 지연 일부를 숨길 수 있습니다.

## 2. 실무 사례

### 사례 1. 반복문 순서만 바꿨는데 속도가 달라진다

```java
// A. 한 행을 끝까지 읽고 다음 행으로 이동
for (int row = 0; row < rows; row++) {
    for (int col = 0; col < cols; col++) {
        sum += matrix[row][col];
    }
}

// B. 여러 행을 오가며 같은 열을 읽음
for (int col = 0; col < cols; col++) {
    for (int row = 0; row < rows; row++) {
        sum += matrix[row][col];
    }
}
```

둘 다 **O(rows × cols)** 이지만, 데이터를 방문하는 순서가 다릅니다.

| | A: 행 순회 | B: 열 순회 |
|---|---|---|
| 접근 순서 | `[0][0] → [0][1] → [0][2]` | `[0][0] → [1][0] → [2][0]` |
| 캐시 활용 | 함께 가져온 옆 원소를 바로 사용 | 옆 원소를 사용하기까지 시간이 걸림 |
| 결과 | 공간 지역성을 활용하기 쉬움 | 재사용 전에 라인이 밀려날 수 있음 |

**Java에서 주의:** `int[][]`는 행마다 별도의 `int[]`를 참조하는 구조입니다. 일반적인 JVM에서는 한 행의 원소들이 연속 배치되지만, 모든 행이 한 덩어리로 붙어 있다고 보장되지는 않습니다. [Java 배열 명세](https://docs.oracle.com/javase/specs/jls/se21/html/jls-10.html)

> **면접 포인트:** 같은 시간 복잡도라도 메모리 접근 순서에 따라 실행 시간이 달라질 수 있다.

### 사례 2. ArrayList와 LinkedList는 둘 다 O(N) 순회인데 왜 차이가 날까?

```text
ArrayList  : [참조 A][참조 B][참조 C] → 참조들을 연속해서 읽음
LinkedList: [노드 A] → [노드 B] → [노드 C] → next를 따라 이동
```

- **ArrayList:** 참조 배열을 순서대로 읽어 공간 지역성을 활용하기 좋습니다.
- **LinkedList:** 노드가 흩어져 있을 수 있고, 현재 노드를 읽어야 다음 노드의 주소를 알 수 있습니다.

**ArrayList에서 연속 배치되는 것은 객체 자체가 아니라 참조입니다.** `ArrayList<Integer>`와 정수 값이 연속 배치되는 `int[]`는 다릅니다. [OpenJDK 구현](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/util/ArrayList.java)

> **복잡도도 확인!** 반복자로 순회하면 둘 다 O(N)입니다. 하지만 `LinkedList`를 `get(i)`로 반복 순회하면 매번 위치를 찾아가므로 전체 O(N²)이 됩니다. [LinkedList 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/LinkedList.html)

### 사례 3. 스레드별 카운터를 나눴는데도 느리다

```text
같은 캐시 라인: [counterA | counterB]

코어 A의 스레드 → counterA만 수정
코어 B의 스레드 → counterB만 수정
```

**원인:** 변수는 다르지만 캐시 라인이 같아, 서로의 복사본을 무효화할 수 있습니다.

**개선 방법**

- 로컬 변수에 누적한 뒤 마지막에 합칩니다.
- 자주 수정하는 스레드별 데이터를 다른 캐시 라인에 배치합니다.
- 패딩·정렬 적용 시 실제 배치를 확인합니다. 패딩은 메모리 사용량을 늘립니다.

## 3. Deep Dive: 데이터가 CPU에 도착하기까지

### 3-1. 왜 저장 공간을 여러 층으로 나눌까?

`sum += values[i]`를 실행하려면 배열 원소가 필요합니다. **CPU가 계산할 준비를 마쳐도, 데이터가 없으면 그 연산은 기다려야 합니다.**

바리스타가 재료를 빨리 꺼내도록 가까운 선반과 큰 창고를 함께 두는 것과 같습니다.

| 계층 | 역할 | 비유 |
|---|---|---|
| **레지스터** | 명령어가 직접 사용하는 값과 상태 보관 | 손에 든 도구 |
| **L1 캐시** | 코어 가까이에서 빠르게 공급 | 바로 앞 선반 |
| **L2 캐시** | L1보다 큰 캐시 | 옆 수납장 |
| **L3 캐시** | 여러 코어가 공유하는 경우가 많은 캐시 | 공동 냉장고 |
| **RAM** | 실행 중인 코드·데이터 보관 | 넓은 작업 공간 |
| **SSD·HDD** | 파일을 지속적으로 저장 | 장기 보관 창고 |

**일반적인 경향:** 아래로 갈수록 용량과 접근 지연은 커지고, 비트당 비용은 낮아집니다. 캐시 구성과 공유 범위는 CPU마다 다릅니다.

> 레지스터는 명령어가 직접 사용하는 저장 공간입니다. CPU가 레지스터부터 SSD까지 순서대로 검색하는 것은 아닙니다.

**빠른 메모리로 전부 만들면 안 될까?**

| 구분 | **SRAM(Static RAM): 주로 캐시** | **DRAM(Dynamic RAM): 주로 RAM** |
|---|---|---|
| 특성 | 저장된 데이터가 변하지 않는 RAM | 저장된 데이터가 동적으로 변함 |
| 저장 방식 | 여러 트랜지스터로 상태 유지 | 커패시터에 전하 저장 |
| 리프레시 | 필요 없음 | 전하가 새므로 주기적으로 필요 |
| 비용·집적도 | 비싸고 같은 용량에 큰 면적 필요 | 상대적으로 저렴하고 대용량에 유리 |
| 전원이 꺼지면 | 데이터 소실 | 데이터 소실 |

그래서 **SRAM으로 작은 캐시를, DRAM으로 큰 RAM을 구성**합니다.

### 3-2. 배열 원소 하나를 읽는 과정

CPU가 `values[0]`, `values[1]`을 차례로 읽는다고 해봅시다. 처음에는 배열 데이터가 **RAM에만 있고 관련 캐시에는 없다**고 가정합니다.

| 단계 | 내부에서 하는 일 |
|---|---|
| **① 캐시 확인** | `values[0]`을 L1에서 찾고, 없으면 L2·L3 등 다음 계층에 요청 |
| **② RAM에서 가져오기** | 이 예시에서는 캐시에 없으므로 RAM에서 **주변 데이터까지 한 라인으로** 가져옴 |
| **③ 값 사용** | CPU가 `values[0]`으로 연산하고, 함께 가져온 데이터는 캐시에 보관 |
| **④ 다음 원소 읽기** | `values[1]`도 같은 라인에 있고 유효하게 남아 있다면 캐시에서 바로 사용 |

```text
첫 원소 읽기 → 캐시에 없음 → RAM에서 주변 데이터도 함께 가져옴
다음 원소 읽기 → 함께 가져온 데이터에 있음 → 캐시에서 사용
```

- **히트(Hit):** 해당 캐시에 데이터가 있어 사용합니다.
- **미스(Miss):** 해당 캐시에 없어 다음 계층 등에 요청합니다.

**배열을 순서대로 읽으면 함께 가져온 옆 데이터를 활용하기 좋습니다. 이것이 공간 지역성입니다.**

> L1 미스가 곧 RAM 접근은 아닙니다. L2·L3나 다른 코어의 캐시에서 해결될 수도 있습니다. [캐시 계층 참고](https://cvw.cac.cornell.edu/code-optimization/cache-considerations/multicore-cache-sharing)

<details>
<summary>이해 보충: 64바이트에 정수 16개가 들어가는 이유와 주소 계산</summary>

메모리를 **한 칸에 1바이트가 들어가는 사물함**이라고 생각해 봅시다. 메모리 주소는 각 사물함의 번호입니다.

| 예시 조건 | 사물함으로 이해하면 |
|---|---|
| 정수 하나는 **4바이트** | 정수 하나를 저장하려면 **4칸**이 필요 |
| 캐시 라인은 **64바이트** | 캐시는 **64칸 분량의 데이터를 한 묶음**으로 가져옴 |
| 배열이 **라인 경계에서 시작** | 배열의 첫 원소가 **묶음의 맨 앞**에서 시작 |

이 조건에서는 **64바이트 ÷ 4바이트 = 정수 16개**가 한 묶음에 들어갑니다.

```text
한 캐시 라인 = 64바이트
[values[0]][values[1]] ... [values[15]]
    4B         4B             4B
↑
묶음의 시작 = 배열의 시작
```

**배열이 묶음 중간에서 시작하면 어떨까요?** 앞의 16바이트를 다른 데이터가 차지한다면, 첫 라인에는 정수 12개만 들어갑니다.

```text
한 캐시 라인 = 64바이트
[다른 데이터 16바이트][values[0] ~ values[11]: 48바이트]
                     ↑ 배열 시작
```

그래서 이 예시에서는 설명하기 쉽도록 **배열이 묶음의 맨 앞에서 시작한다**고 정한 것입니다.

`0x1000`은 배열이 시작하는 위치에 붙인 예시 주소입니다. `0x`는 **16진수 표기**라는 뜻이며, 지금은 “배열의 첫 원소가 있는 위치”로 읽으면 됩니다.

> 처음에는 배열 데이터가 **RAM에만 있고 캐시에는 없다**고 가정합니다. 첫 읽기에서 RAM으로 가져오러 가는 과정을 보기 위해서입니다. 프로그램의 주소를 실제 메모리 주소로 바꾸는 **주소 변환 과정은 생략**하고, 캐시에서 데이터를 찾는 흐름에 집중합니다.

**주소 계산 예시**

CPU는 배열의 시작 위치에서 원소 크기만큼 이동해 읽을 위치를 계산합니다. 정수 하나가 4칸을 차지하므로, 다음 정수의 주소는 4만큼 증가합니다.

```text
원소 주소 = 시작 주소 + 인덱스 × 원소 크기
values[0]의 주소 = 0x1000 + 0 × 4 = 0x1000
values[1]의 주소 = 0x1000 + 1 × 4 = 0x1004
```

</details>


### 3-3. 캐시는 무엇을 남겨 두고, 무엇을 미리 가져올까?

| 원리 | 동작 흐름 |
|---|---|
| **시간 지역성** | 작은 배열을 읽음 → 캐시에 보관 → 다시 읽을 때 재사용 |
| **공간 지역성** | `values[0]`을 읽음 → 주변 원소도 함께 가져옴 → `values[1]`에 활용 |
| **프리페치** | 순차 접근 감지 → 아직 요청하지 않은 다음 라인을 미리 가져옴 |

시간 지역성은 **같은 주소**, 공간 지역성은 **가까운 주소**를 다시 활용하는 패턴입니다. [지역성 참고](https://www.cs.cornell.edu/courses/cs3410/2026sp/notes/caches.html)

프리페치는 요청 전에 데이터를 가져오는 기술입니다. 예측이 맞으면 대기를 줄이지만, 틀리면 대역폭과 캐시 공간을 낭비할 수 있습니다.

> 반복 변수 `i`나 누적값 `sum`은 레지스터에 유지될 수도 있습니다. 매번 캐시에서 읽는다고 단정하지 않습니다.

### 3-4. 캐시가 꽉 차면 어떻게 될까?

**기존 라인을 내보내고 새 라인을 넣습니다.** 이를 **축출(Eviction)** 이라고 합니다.

많은 캐시는 여러 **세트(Set)** 로 나뉩니다. 주소에 따라 들어갈 세트가 정해지므로, 다른 세트에 빈자리가 있어도 특정 세트에서는 교체가 필요할 수 있습니다.

| 미스 종류 | 이유 |
|---|---|
| 최초 접근 미스 | 아직 가져온 적 없는 데이터 |
| 용량 미스 | 재사용할 데이터가 캐시에 다 들어가지 않음 |
| 충돌 미스 | 같은 세트에 들어갈 라인들이 자리를 경쟁 |

교체 정책은 내보낼 라인을 고르는 규칙입니다. 최근 사용 여부 등을 활용하지만, 모든 CPU가 정확한 LRU를 쓰지는 않습니다. 멀티코어에서는 다른 코어의 쓰기로 라인이 무효화되는 경우도 있습니다. 

### 3-5. 캐시에서 값을 바꾸면 RAM도 바로 바뀔까?

**쓰기 정책에 따라 다릅니다.**

| 정책 | 동작 | 특징 |
|---|---|---|
| **Write-through** | 캐시 수정 → 다음 계층에도 쓰기 전달 | 쓰기 트래픽이 많아짐 |
| **Write-back** | 캐시 먼저 수정 → 축출 등 필요한 때 다음 계층에 반영 | 반복 쓰기를 묶을 수 있음 |

Write-back에서 `values[0] = 10`을 실행해 봅시다.

```text
① 라인 확보   → values[0]이 들어 있는 라인을 준비
② 값 수정     → 캐시의 값을 10으로 변경
③ Dirty 표시 → 다음 계층에 아직 반영하지 않았음을 기록
④ 나중에 반영 → 축출 등 필요한 때 수정된 데이터를 전달
```

**Dirty는 “다음 계층에 아직 반영하지 않은 수정 내용이 있음”이라는 표시입니다.**

<details>
<summary>꼬리 질문: 쓰려는 데이터가 캐시에 없다면?</summary>

- **Write-allocate:** 라인을 캐시에 가져온 뒤 씁니다.
- **No-write-allocate:** 해당 캐시에 라인을 넣지 않고 다음 계층으로 쓰기를 전달합니다.

이는 Write-through·Write-back과 별개의 선택입니다.

</details>

### 3-6. 면접 전 확인할 표현

| 이렇게 단정하지 않기 | 이렇게 설명하기 |
|---|---|
| 캐시 미스 → 무조건 RAM | 다음 캐시 계층 등에서 해결될 수 있음 |
| 캐시 히트 → 지연 없음 | RAM보다 빠르지만 접근 시간은 필요 |
| 캐시 미스 → CPU 전체 정지 | 데이터에 의존하는 실행이 지연됨 |
