# 컴파일과 인터프리터: 코드가 실행되는 원리


## 1. 면접 핵심 Q&A

### Q1. 컴파일과 인터프리트는 어떻게 다른가요?

* **컴파일은 코드를 다른 형태의 코드로 변환하는 작업이고, 인터프리트는 실행기가 명령을 읽고 그 동작을 수행하는 방식입니다.** 컴파일 결과는 기계어뿐 아니라 바이트코드 같은 중간 코드일 수도 있습니다.

### Q2. Java 코드는 어떻게 실행되나요?

* **`javac`가 소스를 바이트코드로 컴파일하고, JVM이 이를 실행합니다.** 일반적인 HotSpot JVM은 인터프리터로 바이트코드를 처리하고, 자주 실행되는 부분 등을 JIT로 기계어로 만들어 실행할 수 있습니다.

### Q3. 인터프리터도 기계어를 실행하는데 JIT는 왜 필요한가요?

* **인터프리터는 바이트코드를 읽고 처리 동작을 선택하는 과정도 반복합니다.** JIT는 해당 동작을 수행하는 기계어를 만들어, 이후 실행에서 이 선택 과정을 줄입니다.

### Q4. `javac`·네이티브 AOT·JIT는 어떻게 구분하나요?

* **시점과 결과물을 함께 봅니다.** `javac`는 실행 전에 바이트코드를 만들고, 네이티브 AOT는 실행 전에 기계어까지 만듭니다. JIT는 프로그램이 실행되는 중에 기계어를 만듭니다.

### Q5. Java도 네이티브 AOT를 쓸 수 있는데 왜 인터프리터와 JIT를 함께 쓰나요?

* **먼저 실행하면서 자주 쓰이는 부분을 골라 성능을 개선할 수 있기 때문입니다.** 네이티브 AOT는 시작 시간·메모리 사용량에서 유리할 수 있지만, 배포 환경과 라이브러리 호환성을 함께 고려해야 합니다.

## 2. 실무 사례

> 아래는 원리를 설명하는 **학습용 가상 사례**입니다. 

### 사례 1. 새 Spring Boot 서버의 초기 응답이 느리다

**상황:** 배포 직후 요청이 느리고, 같은 요청을 반복하면 응답 시간이 줄어듭니다.

**원인 후보:** 필요한 클래스 파일을 메모리로 읽고 초기값을 준비하는 작업, DB 연결, 애플리케이션 캐시 준비, JIT 컴파일 등이 영향을 줄 수 있습니다. JIT 작업도 CPU를 사용하므로 초기 지연을 모두 인터프리터 탓으로 단정하지 않습니다. [클래스 로딩·초기화](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html), [HotSpot 컴파일](https://docs.oracle.com/en/java/javase/21/vm/java-hotspot-virtual-machine-performance-enhancements.html)

**판단과 개선:** 초기와 안정화 후의 응답 시간·CPU 사용량·DB 대기를 비교합니다. 초기 준비가 원인이라면 실제 업무 경로를 미리 실행하는 **웜업**을 검토합니다. 주문·결제처럼 상태를 바꾸는 요청은 테스트 데이터나 부작용 없는 경로를 사용합니다.

### 사례 2. CPU가 다른 서버에 같은 JAR를 배포한다

**상황:** Java 클래스 파일과 관련 파일을 묶은 **JAR**를 ARM 개발 PC에서 만들어 x86-64 서버에 배포합니다. 두 CPU의 명령어 체계는 다릅니다.

**이유:** 일반적인 `.class` 파일에 들어 있는 것은 특정 CPU의 기계어가 아닌 JVM 바이트코드입니다. 서버에 맞는 JVM이 이를 실행합니다. [JVM과 플랫폼 독립성](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-1.html#jvms-1.2)

**확인할 조건:** 서버 JVM이 클래스 파일 버전을 지원하고 필요한 라이브러리가 있어야 합니다. 별도의 기계어 라이브러리를 사용한다면 그 파일도 서버 OS·CPU에 맞아야 합니다. [클래스 파일 버전](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.3.5), [네이티브 메서드 연결](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.6)

## 3. Deep Dive: 용어부터 실행 흐름까지

### 3-1. 컴파일과 인터프리터는 각각 무엇을 할까?

사람이 쓴 프로그램을 **소스 코드**, CPU가 실행하는 명령을 **기계어**라고 합니다. CPU는 `a + b`라는 글자를 그대로 실행하지 못하므로, 이 뜻을 실제 덧셈 동작으로 연결해야 합니다.

**<u>컴파일은 코드를 다른 형태로 바꾸는 작업</u>**, <u>**컴파일러는 그 작업을 하는 프로그램**입니다.</u> 덧셈하는 기계어를 미리 만들어 두고 나중에 실행할 수 있습니다. 결과가 기계어 대신 다른 실행 프로그램이 이해하는 **중간 코드**일 수도 있습니다.

**<u>인터프리터는 코드를 읽고 지시대로 동작하는 프로그램**입니다.</u> 덧셈 지시를 읽으면 자신에게 준비된 덧셈 처리 기능을 사용합니다. 이 실행 방식을 **인터프리트**라고 합니다.

**인터프리터 자체는 이미 실행 가능한 프로그램**이므로, 입력 코드를 먼저 기계어로 만들 필요는 없습니다. 컴파일 결과가 기계어라면 CPU가 직접 실행하고, 중간 코드라면 이를 이해하는 인터프리터가 처리할 수 있습니다.

### 3-2. AOT와 JIT는 ‘언제 컴파일하는가’의 차이

<u>컴파일을 **프로그램 실행 전에** 하면 AOT(Ahead-Of-Time)</u>, <u>**실행 중에** 하면 JIT(Just-In-Time)</u>라고 합니다. JIT는 프로그램이 끝난 후가 아니라 돌아가는 도중에 컴파일한다는 뜻입니다.

<u>특정 CPU용 기계어를 **네이티브 기계어**</u>라고도 합니다. 이 문서에서는 중간 코드만 미리 만드는 경우와 구분해, <u>실행 전에 **기계어까지** 만드는 방식을 **네이티브 AOT**</u>라고 부릅니다.

한 프로그램에서 컴파일과 인터프리트를 함께 사용할 수도 있습니다. Java의 실행 과정을 보면 이 관계가 더 분명해집니다.

### 3-3. Java의 바이트코드와 JVM에서 `add(2, 3)` 따라가기

CPU 종류가 다르면 이해하는 기계어도 다릅니다. Java는 공통된 중간 명령어인 **바이트코드**를 만들고, 각 환경에 맞는 실행 프로그램인 **JVM(Java Virtual Machine, 자바 가상 머신)**이 이를 처리하게 합니다. 바이트코드는 CPU가 직접 실행하는 명령어가 아닙니다.

다음은 두 정수를 더하는 Java 메서드입니다. `add(2, 3)`으로 호출하면 `a`에 2, `b`에 3이 전달되고, `return`은 결과 5를 호출한 곳으로 돌려줍니다.

```java
static int add(int a, int b) {
    return a + b;
}
```

**먼저 실행할 코드를 준비합니다.**

1. **Java 컴파일러 `javac`:** 소스를 바이트코드가 담긴 `.class` 파일로 바꿉니다. 아직 CPU용 기계어를 만든 것은 아닙니다.
2. **JVM에서 실행 준비:** JVM이 클래스 파일을 읽고 검사와 초기 설정 등을 합니다.
3. **바이트코드 실행:** JVM이 준비된 명령을 처리합니다. 아래에서는 널리 쓰이는 JVM 구현인 **HotSpot**의 인터프리터·JIT 경로를 비교합니다. [javac 문서](https://docs.oracle.com/en/java/javase/21/docs/specs/man/javac.html), [클래스 실행 준비](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html)

**① `javac` 컴파일은 끝났지만, `add`의 JIT 컴파일은 아직 하지 않은 상태**

CPU가 **인터프리터의 기계어**를 실행하면 다음 과정이 진행됩니다. 실제 기계어 대신 동작을 풀어 쓴 흐름입니다.

```text
첫 값 가져오기 명령 읽기 → 처리 코드 선택 → a의 값 2 준비
둘째 값 가져오기 명령 읽기 → 처리 코드 선택 → b의 값 3 준비
덧셈 명령 읽기            → 처리 코드 선택 → 2 + 3 계산
반환 명령 읽기            → 처리 코드 선택 → 5 반환
```

**`add` 전용 기계어 없이도 인터프리터의 준비된 처리 코드를 사용할 수 있습니다.** 다시 실행할 때도 바이트코드를 읽고 처리 동작을 선택하는 과정은 반복됩니다. 


**② 실행 중 JIT가 `add`를 컴파일한 뒤**

`add`가 반복 실행되어 컴파일 대상으로 선택되었다고 해봅시다. JIT는 바이트코드를 분석해 “전달받은 두 값을 더해 반환하는 기계어”를 만들고, **코드 캐시**라는 메모리 영역에 보관합니다.

```text
준비: JIT가 add의 바이트코드 분석 → 기계어 생성·보관
실행: CPU가 생성된 기계어 실행 → 2와 3을 더함 → 5 반환
```

**JIT가 만든 코드에는 할 일이 정해져 있어, 바이트코드를 읽고 처리 동작을 고르는 과정이 필요 없습니다.** CPU는 두 방식 모두 기계어를 실행하지만, JIT 이후에는 그 추가 작업을 줄입니다. 

다음에 `add(7, 8)`을 호출하면 같은 코드를 사용해 15를 계산할 수 있습니다. 보관한 것은 결과 5가 아니라 **덧셈을 수행하는 코드**입니다. 이 예시에서는 다른 코드와 합치는 최적화 등을 생략했습니다.

### 3-4. `javac`·네이티브 AOT·JIT를 연결하면

**`javac`는 컴파일러 이름이고, AOT는 컴파일 시점을 나타내는 말**입니다. 시점만 보면 `javac`도 사전 컴파일이지만, 결과는 바이트코드입니다. 네이티브 AOT는 실행 전에 기계어까지 만든다는 점이 다릅니다.

Java에서는 **GraalVM Native Image** 같은 도구가 바이트코드 등을 받아 특정 OS·CPU용 실행 파일을 만듭니다. 

| 구분 | 시점 | 이 예시의 입력 → 결과 |
|---|---|---|
| `javac` | 실행 전 | Java 소스 → 바이트코드 |
| 네이티브 AOT: Native Image | 실행 전 | 바이트코드 등 → 기계어를 담은 실행 파일 |
| JIT | 실행 중 | 바이트코드 → 기계어 |

```text
[일반적인 JVM 실행]
실행 전: Java 소스 → javac → 바이트코드
실행 중: JVM이 바이트코드를 인터프리터로 처리
         또는 JIT로 기계어를 만들어 실행

[네이티브 AOT 실행]
실행 전: Java 소스 → javac → 바이트코드 → Native Image → 실행 파일
실행 시: CPU가 미리 만들어 둔 실행 파일의 기계어를 실행
```

즉, Java에서 “처음에는 인터프리터로 처리한다”는 말은 **`javac` 컴파일은 끝났지만 해당 코드의 JIT 컴파일은 아직 하지 않았을 수 있다**는 뜻입니다. 모든 코드가 반드시 JIT 컴파일되는 것도 아닙니다.

### 3-5. 미리 기계어를 만들 수 있는데도 JVM 방식을 쓰는 이유

**컴파일에도 시간과 메모리가 들기 때문입니다.** JVM은 인터프리터로 실행을 시작하고, 자주 쓰이는 부분을 골라 JIT로 성능을 개선할 수 있습니다. 코드를 더 효율적으로 바꾸는 작업을 **최적화**라고 합니다.

학습용 예로 쇼핑몰에서 상품 조회가 반복된다면, 드물게 쓰는 기능보다 상품 조회 코드를 개선하는 효과가 클 수 있습니다. JIT는 실제 실행 정보를 활용하지만, 실행 중 컴파일 비용도 부담합니다. 

**네이티브 AOT는 실행 중 JIT 부담을 줄여 시작 시간·메모리 사용량에서 유리할 수 있습니다.** 대신 어떤 코드가 필요한지 미리 판단해야 합니다. JVM이 실행 중 이름으로 찾아 호출하는 기능 등은 사전 분석으로 놓칠 수 있어, 추가 설정과 라이브러리 호환성 확인이 필요할 수 있습니다. 

| 관점 | JVM의 인터프리터·JIT | 네이티브 AOT: Native Image |
|---|---|---|
| 주된 이점 | 실제 실행 정보를 활용한 최적화, 동적인 기능 처리 | 시작 시간·메모리 사용량을 줄이기 좋음 |
| 주된 부담 | 초기 실행과 실행 중 컴파일 비용 | 사전 빌드, 추가 설정·라이브러리 호환성 확인 |
| 배포 조건 | 클래스 파일·의존성과 호환되는 JVM | 대상 OS·CPU와 실행 환경에 맞는 파일 |

**선택 기준:** 
* 짧게 실행하고 종료되는 작업은 시작 시간이 중요하고, 계속 요청을 처리하는 서버는 안정화 후 응답 시간·처리량도 중요합니다. 
* AOT도 최적화할 수 있으므로 어느 쪽이 항상 빠르다고 단정하지 않고, 같은 기능·부하에서 시간과 메모리를 비교합니다.

<summary>이해 보충: 실제 덧셈 바이트코드는 어떻게 생겼을까?</summary>

JVM은 계산할 값을 **피연산자 스택**에 잠시 쌓습니다. 스택은 나중에 넣은 값을 먼저 꺼내는 공간이며, 아래에서는 오른쪽이 마지막에 넣은 값입니다.

```text
iload_0  → 첫 인수 2를 올림             [2]
iload_1  → 둘째 인수 3을 올림           [2, 3]
iadd     → 두 값을 꺼내 더한 값을 올림  [5]
ireturn  → 결과 5 반환
```

앞의 `static` 메서드에 대한 바이트코드를 사람이 읽는 기호로 표현했습니다. `iadd`는 CPU의 덧셈 명령과 다르며, 소스 한 줄이 여러 바이트코드 명령으로 나뉠 수 있습니다. [JVM 명령어 명세](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-6.html)

<summary>이해 보충: 코드 캐시와 CPU 캐시는 같을까?</summary>

**코드 캐시**는 JVM이 생성한 기계어를 보관하는 메모리 영역입니다. **CPU 캐시**는 메모리의 코드·데이터에 빠르게 접근하도록 하드웨어가 관리하는 저장 공간입니다. JIT로 만든 코드를 실행할 때도 앞서 배운 메모리 계층 구조가 관여합니다. [HotSpot 코드 캐시](https://docs.oracle.com/en/java/javase/21/vm/java-hotspot-virtual-machine-performance-enhancements.html)

</details>

<summary>심화: C1·C2와 인라이닝은 무엇일까?</summary>

HotSpot은 최적화 수준이 다른 컴파일러를 조합하는 **계층형 컴파일**을 사용합니다. C1은 비교적 빠르게 컴파일하고 실행 정보를 수집하는 코드도 만들며, C2는 그 정보를 활용해 더 적극적으로 최적화할 수 있습니다. 모든 메서드가 같은 단계나 고정된 호출 횟수에서 전환되는 것은 아닙니다. [계층형 컴파일](https://docs.oracle.com/en/java/javase/21/vm/java-hotspot-virtual-machine-performance-enhancements.html)

`add(a, b)`의 동작을 호출하는 곳에 포함시키는 최적화를 **인라이닝**이라고 합니다. 호출 비용을 줄이고 주변 코드와 함께 최적화할 수 있어, 실제로는 `add`가 독립된 기계어 함수로 남지 않을 수도 있습니다. [인라이닝 원리](https://www.oracle.com/java/technologies/whitepaper.html)

</details>

<summary>이해 보충: C와 Python에 연결하면?</summary>

**C의 대표적인 네이티브 빌드:** 전처리 → 컴파일 → 어셈블 → 링크를 거칩니다. 헤더·매크로를 반영하고, 어셈블리 코드를 만든 뒤 기계어 등이 담긴 목적 파일로 바꾸고, 다른 코드·라이브러리와 연결합니다. 실행 전에 기계어를 만드는 AOT의 예입니다. [GCC 빌드 단계](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)

**CPython:** 대표적인 Python 실행 프로그램으로, 소스를 바이트코드로 컴파일한 뒤 실행합니다. `.pyc`는 바이트코드 등을 저장해 재컴파일 비용을 줄이는 캐시 파일입니다. 컴파일 단계가 있다고 곧바로 네이티브 실행 방식인 것은 아니며, Python과 Java의 바이트코드도 서로 다릅니다. [Python 바이트코드 설명](https://docs.python.org/3.13/glossary.html#term-bytecode)

</details>
