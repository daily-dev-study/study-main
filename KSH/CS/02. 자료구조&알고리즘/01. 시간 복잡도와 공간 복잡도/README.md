# 시간 복잡도와 공간 복잡도: 코드로 이해하는 빅오

## 1. 면접 핵심 Q&A

### Q1. 시간 복잡도와 공간 복잡도는 무엇인가요?

* **입력 크기가 커질 때 연산 횟수와 필요한 메모리가 늘어나는 정도입니다.** 시간 복잡도는 실행 시간을 몇 초로 예측하는 값이 아닙니다. 공간 복잡도는 입력을 포함한 전체 공간인지, 입력 외에 필요한 **보조 공간**인지 범위를 밝혀야 합니다.

### Q2. 빅오 표기법은 무엇이고, 왜 상수를 생략하나요?

* **빅오는 입력이 충분히 커졌을 때 증가율의 상한을 나타내는 표기법입니다.** 예를 들어 `3N + 2`는 `O(N)`으로 표현합니다. 상수 배율과 작은 항을 생략하면 입력 증가에 따른 큰 흐름을 비교할 수 있습니다. 실제 속도를 비교할 때는 이 상수 비용도 중요합니다.

### Q3. 빅오는 최악의 경우를 뜻하나요?

* **아닙니다. 최선·평균·최악은 분석할 상황이고, 빅오는 그 분석 결과를 표현하는 방법입니다.** 선형 탐색은 첫 원소에서 찾으면 최선 `O(1)`, 끝까지 확인해야 하면 최악 `O(N)`입니다. 평균도 입력 분포를 가정해 분석할 수 있습니다. [점근적 분석과 경우별 분석](https://www.cs.cornell.edu/courses/cs312/2004fa/lectures/lecture16.htm)

### Q4. 반복문이 두 개면 O(N²)인가요?

* **각 반복문이 몇 번 실행되는지 봐야 합니다.** `N`번 도는 반복문 두 개를 차례로 실행하면 `2N`이므로 `O(N)`입니다. 바깥 반복 `N`번마다 안쪽 반복도 `N`번씩 실행하면 `O(N²)`입니다.

### Q5. 이진 탐색은 왜 O(log N)인가요?

* **한 번 비교할 때마다 남은 탐색 범위를 대략 절반으로 줄이기 때문입니다.** `N`개를 계속 절반으로 나눠 하나 정도만 남길 때까지의 횟수가 약 `log₂N`입니다. 정렬된 배열에서 각 단계의 비교와 중앙 원소 접근이 일정한 비용이라는 조건입니다.

### Q6. 같은 O(N)인 코드도 실행 시간이 다른 이유는 무엇인가요?

* **반복 한 번의 비용과 메모리 접근 방식이 다를 수 있기 때문입니다.** 복잡도에서 생략한 상수 비용에 더해 캐시 적중 여부, 객체 할당, JIT 최적화 등이 영향을 줍니다. 복잡도로 입력 증가에 따른 부담을 비교하고, 실제 환경에서 성능을 측정합니다.

### Q7. 시간을 줄이기 위해 공간을 더 쓰는 예시는 무엇인가요?

* **매번 목록을 훑는 대신 조회용 HashSet을 만드는 경우입니다.** 주문 `N`건과 차단 ID `M`개를 대조할 때, 최악 `O(NM)`의 목록 탐색을 집합 생성까지 포함한 기대 시간 `O(N + M)`으로 바꿀 수 있습니다. 대신 조회용 집합에 `O(M)`의 추가 공간이 필요합니다. 해시가 적절히 분산된다는 조건입니다. [HashSet의 성능 조건](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/HashSet.html)

<details>
<summary>심화 Q&A: ArrayList의 add는 왜 분할 상환 O(1)인가요?</summary>

끝에 원소를 추가할 때 빈자리가 있으면 바로 넣지만, 내부 배열이 꽉 차면 더 큰 배열을 마련하고 기존 원소를 복사해야 합니다. 이 한 번의 추가는 `O(N)`이 될 수 있습니다.

그러나 배열 확장은 매번 일어나지 않습니다. 빈 리스트부터 `N`개를 연속으로 추가하는 전체 비용이 `O(N)`이므로, 이를 추가 횟수로 나눈 **분할 상환 비용**은 `O(1)`입니다. 무작위 입력을 가정하는 평균 분석과 달리, 여러 연산을 묶어 비용을 나누어 보는 방식입니다. [ArrayList 공식 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/ArrayList.html)

</details>

## 2. 실무 사례

### 주문마다 차단 목록 전체를 검색한다

> 원리를 설명하는 **학습용 가상 사례**입니다. 특정 서비스의 장애나 성능 측정 결과가 아닙니다.

* **상황:** 주문 목록에서 차단된 사용자의 주문만 추립니다. 주문 수는 `N`, 차단 ID 수는 `M`이며, 두 목록은 이미 메모리에 있습니다. Java의 차단 목록은 `ArrayList<Long>`, Python의 차단 목록은 정수 ID를 담은 `list`입니다. Python 주문 객체에서는 `order.user_id`로 사용자 ID를 읽는다고 가정합니다.

**Java**

```java
List<Order> blockedOrders = orders.stream()
    .filter(order -> blackListUserIds.contains(order.getUserId()))
    .collect(Collectors.toList());
```

**Python**

```python
blocked_orders = [
    order for order in orders
    if order.user_id in blacklist_user_ids
]
```

**<원인>**

Java의 `ArrayList.contains()`와 Python의 리스트에 대한 `in`은 목록을 앞에서부터 확인합니다. 찾는 ID가 없으면 `M`개를 모두 확인해야 합니다. 주문마다 이 탐색을 반복하므로, 최악에는 `N × M`번의 ID 비교가 필요합니다. Stream이나 리스트 컴프리헨션으로 짧게 작성해도 내부 탐색 방식은 바뀌지 않습니다. [ArrayList 연산 비용](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/ArrayList.html), [CPython 리스트 구현의 list_contains](https://github.com/python/cpython/blob/3.14/Objects/listobject.c)

주문이 3건이고 차단 ID가 4개라면, 모두 차단 목록에 없는 경우 `4 + 4 + 4 = 12`번 비교합니다. 두 목록의 크기가 각각 두 배가 되면 `6 × 8 = 48`번으로 늘어납니다. **양쪽 크기가 함께 늘어날 때 부담이 빠르게 커지는 이유**입니다.

**<개선>** 

차단 ID로 조회할 위치를 빠르게 찾을 수 있도록 Java에서는 `HashSet`, Python에서는 `set`을 한 번 만듭니다. 해시는 값을 바탕으로 저장·검색할 위치를 정하는 데 사용하는 계산입니다. 값이 여러 위치에 잘 분산되면 매번 목록 전체를 훑지 않아도 됩니다.

**Java**

```java
Set<Long> blackListSet = new HashSet<>(blackListUserIds);

List<Order> blockedOrders = orders.stream()
    .filter(order -> blackListSet.contains(order.getUserId()))
    .collect(Collectors.toList());
```

**Python**

```python
blacklist_set = set(blacklist_user_ids)

blocked_orders = [
    order for order in orders
    if order.user_id in blacklist_set
]
```

1. 차단 ID `M`개를 읽어 집합을 만듭니다: 기대 시간 `O(M)`.
2. 주문 `N`건을 순회하며 집합에서 ID를 조회합니다: 조회당 기대 `O(1)`, 합계 `O(N)`.
3. 두 작업을 차례로 수행하므로 전체 기대 시간은 **O(M + N)**입니다.

여기서 상수 시간 조회는 **해시가 적절히 분산되는 조건**에 기반합니다. Python도 CPython의 해시 테이블 기반 `set`을 기준으로 같은 방식으로 분석합니다. 실제 CPU 명령어 수나 실행 시간을 뜻하지 않습니다. [HashSet 공식 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/HashSet.html), [CPython set 구현](https://github.com/python/cpython/blob/3.14/Objects/setobject.c)

**<추가 공간>** 

집합에는 최대 `M`개의 서로 다른 ID를 저장하므로 `O(M)`이 필요합니다. 반환할 주문이 `K`건이라면 결과 목록에도 `O(K)` 공간이 필요하며, 이는 두 방식 모두에 해당합니다. 따라서 입력을 제외하고 결과까지 포함하면 기존 방식은 `O(K)`, 개선 방식은 `O(M + K)`입니다. 결과 목록은 기존 `Order` 객체의 참조를 담으며, 주문 객체 전체를 복제하지 않습니다.

**<판단 기준>** 

조회 횟수가 많을수록 집합을 미리 만드는 비용을 감수할 이유가 커집니다. 아주 작은 목록을 한 번만 조회한다면 생성 비용 때문에 단순 탐색이 더 빠를 수도 있습니다. 실제 입력 크기, 반복 조회 횟수, 메모리 여유를 함께 확인합니다.

<details>
<summary>심화: 조회용 집합을 요청 간 캐시로 공유한다면?</summary>

요청마다 집합을 만드는 비용을 줄일 수 있지만, 차단 목록이 바뀌었을 때 이전 정보가 남는 문제가 생깁니다. 갱신 시점이나 만료 시간을 정하고, 여러 요청이 동시에 읽고 갱신하는 방식도 설계해야 합니다.

일반적인 결과 캐시라면 최대 크기와 항목을 내보내는 정책도 필요합니다. 다만 **차단 여부 판단에 쓰는 집합에서 항목을 임의로 제거하고 ‘없으면 허용’으로 처리하면 판단이 달라집니다.** 캐시에 없을 때 원본 저장소를 확인할지, 전체 목록을 일관되게 교체할지 등 데이터의 용도에 맞게 결정합니다.

캐시에 계속 참조되는 객체는 더 이상 필요 없더라도 GC가 회수할 수 없습니다. 캐시를 도입할 때는 조회 속도뿐 아니라 보관할 데이터의 양과 수명도 관리해야 합니다.

</details>

3. Deep Dive: 입력이 늘면 무엇이 달라질까?

### 3-1. 실행 시간을 재면 되는데, 왜 복잡도가 필요할까?

원소가 10개인 배열에서 값을 찾을 때는 앞에서부터 하나씩 확인해도 부담이 작습니다. 하지만 배열이 커지면 원하는 값을 찾기 전에 확인해야 할 원소도 많아질 수 있습니다. 작은 입력에서 빨랐다는 사실만으로 큰 입력에서도 빠를 것이라고 판단하기 어렵습니다.

그래서 먼저 **입력 크기와 해야 할 일의 관계**를 살펴봅니다. 배열의 원소 수를 `N`이라고 정하고, <u>`N`이 늘어날 때 비교나 덧셈 같은 기본 연산의 횟수가 어떻게 늘어나는지 분석합니다. 이것이 시간 복잡도를 구하는 출발점입니다.</u> 

**Java**

```java
static long sum(int[] values) {
    long total = 0;
    for (int i = 0; i < values.length; i++) {
        total += values[i];
    }
    return total;
}
```

**Python**

```python
def sum_values(values):
    total = 0
    for i in range(len(values)):
        total += values[i]
    return total
```

이 코드는 각 원소를 한 번씩 읽어 더합니다. `N`이 10이면 덧셈 10번, 100이면 100번입니다. 반복 조건 확인과 인덱스 증가까지 세어도 전체 일은 `N`에 비례해 늘어납니다.

**중요한 것은 정확한 기계어 명령어 개수가 아니라 증가 방식입니다.** CPU·JVM에 따라 한 번의 처리 비용은 달라지지만, 이 코드가 모든 원소를 훑는다는 구조를 먼저 파악할 수 있습니다.

### 3-2. N번과 2N번은 왜 둘 다 O(N)일까?

**2N이 N으로 계산되는 것은 아닙니다.** <u>**실제 작업량은 2N번 그대로이고, `O(N)`은 입력이 커질 때 작업량이 늘어나는 방식을 나타냅니다.**</u> 우선 짧은 문자열을 출력하는 횟수만 세어 봅시다. 출력 한 번을 일정한 비용의 작업으로 보는 학습용 예시입니다.

**1) 반복할 때마다 한 번 출력하면 N번**

**Java**

```java
int n = 3;
for (int i = 0; i < n; i++) {
    System.out.println("안녕");
}
```

**Python**

```python
n = 3
for i in range(n):
    print("안녕")
```

두 코드 모두 반복문이 3번 돌고, 한 번 돌 때마다 한 번 출력합니다. `n = 3`이면 3번, `n = 6`이면 6번이므로 출력 횟수는 **N번**입니다.

**2) 반복할 때마다 두 번 출력하면 2N번**

**Java**

```java
int n = 3;
for (int i = 0; i < n; i++) {
    System.out.println("안녕");
    System.out.println("반가워");
}
```

**Python**

```python
n = 3
for i in range(n):
    print("안녕")
    print("반가워")
```

이번에는 반복 한 번에 두 번씩 출력합니다. `n = 3`이면 첫 반복에서 2번, 두 번째에서 2번, 세 번째에서 2번으로 **총 6번**입니다. 입력이 N이면 출력은 **2N번**입니다.

**3) 작업 횟수는 다르지만, 늘어나는 방식은 같다**

| 입력 크기 N | 첫 번째 코드: N번 | 두 번째 코드: 2N번 |
|---|---:|---:|
| 3 | 3번 | 6번 |
| 6 | 6번 | 12번 |
| 12 | 12번 | 24번 |

표를 아래로 읽으면, **입력이 두 배가 될 때 두 코드 모두 출력 횟수가 두 배**가 됩니다. 입력에 비례해 작업량이 늘어나는 것을 **선형 증가**라고 하며, 두 코드 모두 `O(N)`으로 표현합니다. 반복 조건 확인과 인덱스 증가를 포함해도 N에 비례하는 흐름은 같습니다.

즉, **‘N번과 2N번은 같은 횟수’가 아니라 ‘같은 방식으로 증가한다’**는 뜻입니다. 앞의 숫자 2를 생략하는 이유는 정확한 횟수보다 증가율을 비교하기 위해서입니다. 실제 성능을 비교할 때는 이런 작업량 차이도 중요합니다.

<details>
<summary>이해 보충: 3N + 2와 ‘점근적 상한’은 어떻게 연결될까?</summary>

원소마다 3번씩 처리하고 마무리 작업을 2번 하면 작업량은 `3N + 2`입니다. N이 커질수록 고정된 마무리 작업의 영향은 작아지고, 전체는 N에 비례해 증가하므로 `O(N)`으로 표현합니다.

이를 수학적으로 설명하려면 `4N`을 기준선으로 잡아 볼 수 있습니다. `N = 1`에서는 작업량 5가 기준선 4를 넘지만, **N이 2 이상이면 항상 `3N + 2 ≤ 4N`**입니다. `2 ≤ N`이므로 `3N + 2 ≤ 3N + N`이기 때문입니다.

빅오에서 `O(N)`은 어떤 입력 크기 이후부터 작업량이 N의 고정된 배수를 넘지 않는다는 뜻입니다. 여기서는 배수 4를 바꾸지 않아도 `N ≥ 2`부터 이 조건이 유지됩니다. 이렇게 어느 기준점 이후에 적용되는 증가율의 상한을 **점근적 상한**이라고 합니다. [빅오의 정의](https://www.cs.cornell.edu/courses/cs312/2004fa/lectures/lecture16.htm)

</details>

<details>
<summary>이해 보충: O(N)인 코드를 O(N²)이라고 해도 맞을까?</summary>

상한이라는 정의만 보면 맞습니다. 선형으로 늘어나는 비용은 충분히 큰 입력에서 어떤 상수배의 `N²`보다도 작기 때문입니다. 다만 너무 느슨한 상한은 실제 증가를 설명하는 데 도움이 적습니다.

면접과 이 문서에서는 특별한 언급이 없으면 가능한 한 증가를 잘 나타내는 상한을 답합니다. 위와 아래를 같은 증가율로 묶어 표현하는 기호는 **Θ(세타)**이고, 하한을 나타내는 기호는 **Ω(오메가)**입니다. 이 기호 자체가 각각 평균·최선의 경우를 뜻하는 것은 아닙니다. [MIT 점근적 표기법 자료](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-fall-2011/ce8348ec64dce3841ced6a9d0c9e48f2_MIT6_006F11_rec01.pdf)

</details>


### 3-3. 같은 탐색도 언제 찾느냐에 따라 달라진다

배열에서 `7`을 찾는다고 해 봅시다. 첫 번째 원소가 `7`이면 비교 한 번으로 끝납니다. 반대로 배열에 `7`이 없으면 마지막 원소까지 확인해야 합니다.

- **최선의 경우:** 첫 원소에서 발견합니다. 입력 크기와 관계없이 비교 한 번이므로 `O(1)`입니다.
- **최악의 경우:** 끝까지 확인합니다. 원소 수만큼 비교하므로 `O(N)`입니다.
- **평균적인 경우:** 각 상황이 얼마나 자주 일어나는지 가정해야 합니다. 예를 들어 값이 정확히 한 곳에 있고 모든 위치에서 같은 확률로 발견된다면, 평균 비교 횟수는 `(N + 1) / 2`로 `O(N)`입니다.

따라서 **어떤 경우를 분석할지 먼저 정하고, 그 비용을 빅오로 표현합니다.** 별도 가정 없이 “평균적으로 절반만 보면 된다”라고 단정하지 않습니다.


### 3-4. 반복문은 개수가 아니라 실행 횟수를 센다

두 반복문이 **차례로** 실행되면 횟수를 더합니다.

**Java**

```java
long total = 0;
for (int i = 0; i < n; i++) {
    total += a[i];
}
for (int j = 0; j < m; j++) {
    total += b[j];
}
```

**Python**

```python
total = 0
for i in range(n):
    total += a[i]
for j in range(m):
    total += b[j]
```

첫 배열에서 `N`번, 두 번째 배열에서 `M`번 더하므로 `O(N + M)`입니다. 두 배열의 길이가 모두 `N`일 때는 `O(2N)`, 즉 `O(N)`으로 정리됩니다.

반면 바깥 반복마다 안쪽 반복을 처음부터 끝까지 실행하면 횟수를 곱합니다.

**Java**

```java
long matches = 0;
for (int i = 0; i < n; i++) {
    for (int j = 0; j < m; j++) {
        if (a[i] == b[j]) {
            matches++;
        }
    }
}
```

**Python**

```python
matches = 0
for i in range(n):
    for j in range(m):
        if a[i] == b[j]:
            matches += 1
```

`a[0]`을 `b`의 `M`개와 비교하고, `a[1]`도 다시 `M`개와 비교합니다. 이 일을 `N`개 원소에 대해 반복하므로 비교 횟수는 `N × M`, 시간 복잡도는 `O(NM)`입니다. **입력 크기가 서로 다르면 N과 M을 유지합니다.**

안쪽 반복이 입력과 관계없이 10번만 돈다면 `10N`이므로 중첩 반복이어도 `O(N)`입니다. 또한 반복문 안에서 호출하는 `contains()`나 정렬 메서드의 비용도 포함해야 합니다.

<details>
<summary>이해 보충: 안쪽 반복 범위가 점점 줄어들면?</summary>

모든 사람의 쌍을 한 번씩 확인하려면, 첫 사람은 나머지 `N−1`명, 두 번째 사람은 이미 확인한 쌍을 제외한 `N−2`명과 비교합니다.

**Java**

```java
for (int i = 0; i < n; i++) {
    for (int j = i + 1; j < n; j++) {
        // i와 j의 쌍을 한 번 처리: 한 번의 비용은 O(1)로 가정
    }
}
```

**Python**

```python
for i in range(n):
    for j in range(i + 1, n):
        # i와 j의 쌍을 한 번 처리: 한 번의 비용은 O(1)로 가정
        pass  # 실제 처리 코드를 넣을 자리
```

처리 횟수는 `(N−1) + (N−2) + … + 1 = N(N−1)/2`입니다. 10명이면 45쌍이고, 증가를 이끄는 항은 `N²`이므로 시간 복잡도는 `O(N²)`입니다.

</details>


### 3-5. 절반씩 줄이면 왜 O(log N)일까?

정렬된 배열에서 값을 찾는다면, 처음부터 하나씩 볼 필요가 없습니다. 중앙 값과 비교했을 때 찾는 값이 더 크면 중앙 이하의 값들은 후보에서 제외할 수 있습니다. 작다면 반대쪽을 제외합니다. 이렇게 **정렬된 순서를 이용해 후보를 줄이는 방식**이 이진 탐색입니다.

1. 현재 탐색 범위의 중앙 원소를 읽습니다.
2. 찾는 값과 같으면 종료합니다.
3. 다르면 왼쪽이나 오른쪽 중 가능한 절반만 남깁니다.
4. 남은 범위에서 반복하며, 범위가 비면 값이 없는 것입니다.

후보가 줄어드는 규모를 단순화하면 `16 → 8 → 4 → 2 → 1`입니다. 네 번 절반으로 줄이면 하나가 남습니다. **`log₂16 = 4`는 ‘2로 몇 번 나누면 1이 되는가’를 나타냅니다.** 실제 비교에는 마지막 후보 확인 등이 더해질 수 있지만 증가율은 `O(log N)`입니다. [MIT 이진 탐색 자료](https://www.ocw.mit.edu/courses/6-006-introduction-to-algorithms-fall-2011/90a37c49b07b105ea7a027abc67eddc6_MIT6_006F11_lec03.pdf)

여기에는 배열이 **이미 정렬되어 있다**는 전제가 있습니다. 정렬되지 않은 입력을 한 번 검색하려고 먼저 정렬한다면 정렬 비용까지 포함해야 합니다. 여러 번 검색할 예정이라면 그 준비 비용을 감수할 가치가 있는지 판단합니다.


### 3-6. 대표 복잡도를 증가 방식으로 정리하기

`O(1)`은 한 번의 명령어로 끝난다는 뜻이 아니라 **입력 크기에 따라 일이 늘어나지 않는다**는 뜻입니다. 배열의 특정 인덱스를 읽는 것이 대표적입니다.

`O(N log N)`은 **작게 나눈 뒤 정렬된 순서로 합치는 병합 정렬**로 이해할 수 있습니다. 숫자 8개를 정렬하는 과정을 따라가 봅시다.

**① 숫자가 하나씩 남을 때까지 절반으로 나눕니다**

```text
처음:       [8, 3, 6, 2, 7, 1, 5, 4]
1번 나누기: [8, 3, 6, 2]  [7, 1, 5, 4]
2번 나누기: [8, 3]  [6, 2]  [7, 1]  [5, 4]
3번 나누기: [8] [3] [6] [2] [7] [1] [5] [4]
```

숫자가 하나뿐인 묶음은 이미 정렬된 상태입니다. 이제 이 작은 묶음들을 둘씩 합치면서 전체를 정렬합니다.

**② 합칠 때는 두 묶음의 앞에 남은 숫자를 비교합니다**

예를 들어 정렬된 `[3, 8]`과 `[2, 6]`을 합친다면 다음처럼 진행합니다.

```text
3과 2 비교 → 작은 2를 가져옴
3과 6 비교 → 작은 3을 가져옴
8과 6 비교 → 작은 6을 가져옴
남은 8을 가져옴

결과: [2, 3, 6, 8]
```

각 묶음이 이미 정렬되어 있으므로 앞의 숫자끼리 비교하면 다음에 가져올 숫자를 고를 수 있습니다. 이렇게 합치는 작업을 **병합**이라고 합니다. 숫자를 하나씩 결과에 옮기므로 작업량은 합칠 원소 수에 비례합니다.

**③ 한 단계의 병합 작업을 모두 더하면 N개를 처리합니다**

```text
출발: [8] [3] [6] [2] [7] [1] [5] [4]

합치기 1단계: [3, 8]  [2, 6]  [1, 7]  [4, 5]
→ 2개짜리 결과를 4개 만듦: 2 × 4 = 총 8개 처리

합치기 2단계: [2, 3, 6, 8]  [1, 4, 5, 7]
→ 4개짜리 결과를 2개 만듦: 4 × 2 = 총 8개 처리

합치기 3단계: [1, 2, 3, 4, 5, 6, 7, 8]
→ 8개짜리 결과를 1개 만듦: 8 × 1 = 총 8개 처리
```

묶음은 커지고 묶음 수는 줄지만, **각 단계에서 전체 원소 8개를 한 번씩 결과에 옮긴다**는 점은 같습니다. 원소가 N개라면 한 단계의 작업량은 `O(N)`입니다.

**④ 이런 합치기 단계가 log₂N번 필요합니다**

8개짜리 묶음을 하나씩 나누려면 `8 → 4 → 2 → 1`로 3번 나눕니다. 반대로 합칠 때도 `1 → 2 → 4 → 8`로 3단계가 필요합니다. 이 단계 수가 **`log₂8 = 3`**입니다.

따라서 원소를 결과에 옮기는 횟수는 `8개 × 3단계 = 24번`입니다. 일반화하면 **한 단계의 작업량 N × 단계 수 log₂N**이므로 병합 정렬의 시간 복잡도는 **O(N log N)**입니다. 비교 같은 작업도 있지만, 여기서는 증가 방식을 이해하려고 원소를 옮기는 횟수를 세었습니다. N이 2의 거듭제곱이 아니면 묶음 크기가 조금 달라져도 같은 복잡도로 분석합니다. [MIT 병합 정렬 자료](https://www.ocw.mit.edu/courses/6-006-introduction-to-algorithms-fall-2011/90a37c49b07b105ea7a027abc67eddc6_MIT6_006F11_lec03.pdf)

지금까지 살펴본 증가 방식을 정리하면 다음과 같습니다.

| 표기 | 일이 늘어나는 방식 | 대표 예시·조건 |
|---|---|---|
| `O(1)` | 입력이 늘어도 일정한 규모 | 배열 인덱스 접근 |
| `O(log N)` | 후보를 일정 비율로 줄임 | 정렬된 배열의 이진 탐색, 최악 기준 |
| `O(N)` | 원소 수에 비례 | 배열 전체 합산 |
| `O(N log N)` | 단계별 선형 작업을 로그 규모의 단계만큼 수행 | 일반적인 병합 정렬 |
| `O(N²)` | 두 원소의 조합을 넓게 확인 | 모든 원소 쌍 비교 |

이 표는 **증가 방식의 비교**입니다. `O(N)`이면 실시간 API에 적합하다거나, `O(N²)`이면 반드시 장애가 난다는 기준은 아닙니다. 실제 입력 크기와 처리 한 번의 비용도 알아야 합니다.

<details>
<summary>심화: O(2ᴺ)과 O(N!)은 어떤 상황에서 나올까?</summary>

`N`개 항목마다 ‘선택한다/선택하지 않는다’를 모두 시도하면 조합은 `2ᴺ`개입니다. 각 선택을 재귀적으로 탐색하고 각 노드에서 일정한 작업만 하면 탐색 시간은 `O(2ᴺ)`입니다. 각 결과를 길이 `N`의 목록으로 복사해 모두 저장한다면 그 출력 비용도 별도로 포함해야 합니다.

서로 다른 `N`개의 순서를 모두 나열하면 경우의 수는 `N!`입니다. 모든 순서를 검사하는 알고리즘은 여기에 순서 하나를 검사하는 비용도 곱해야 합니다. 따라서 ‘경우의 수’와 ‘전체 실행 비용’을 구분합니다.

이런 증가는 큰 입력에서 부담이 매우 빠르게 커집니다. 다만 사용 가능한 입력 크기를 보편적인 숫자 하나로 정할 수는 없으며, 탐색을 중간에 줄이는 방법과 작업 비용도 영향을 줍니다.

</details>

### 3-7. 공간 복잡도는 무엇을 세는 걸까?

앞의 Java `sum()`과 Python `sum_values()`는 원소를 `N`개 읽지만, 추가로 사용하는 것은 누적 합과 인덱스 같은 일정한 수의 변수입니다. 따라서 시간은 `O(N)`이어도 **보조 공간은 O(1)**입니다. 이는 앞에서 정한 대로 정수와 중간 결과를 일정한 크기로 보는 분석입니다. Python의 `range()`도 인덱스 `N`개를 리스트로 미리 만들지 않습니다. [Python range 설명](https://docs.python.org/3/library/stdtypes.html#ranges)

반대로 원본과 같은 길이의 배열을 새로 만들어 값을 복사하면, 입력이 두 배로 늘 때 새 배열도 두 배로 커집니다. 이 경우 보조 공간은 `O(N)`입니다.

공간을 답할 때는 다음 범위를 구분합니다.

- **입력 공간:** 이미 전달된 배열이나 목록이 차지하는 공간.
- **보조 공간:** 계산을 위해 추가로 쓰는 임시 배열, 집합, 호출 스택 등.
- **출력 공간:** 반환할 결과를 따로 저장하는 공간. 보조 공간 계산에 포함하는지 별도로 밝힙니다.

`sum()`의 입력 배열까지 포함하면 전체 공간은 `O(N)`이지만, 추가 공간만 묻는다면 `O(1)`입니다. 또한 공간 분석은 보통 **실행 중 동시에 필요한 공간의 최댓값**을 봅니다. 지금까지 생성한 모든 임시 객체의 크기를 누적해서 더하는 것과는 다릅니다. 실제 JVM 메모리 사용량에는 GC의 회수 시점 등도 영향을 줍니다. [공간 복잡도와 계산 범위](https://jhu-dsa.github.io/notes/10-asymptotics/step02.html)

### 3-8. 배열을 만들지 않아도 재귀는 공간을 사용한다

재귀는 메서드가 자기 자신을 호출하는 방식입니다. 호출한 메서드가 아직 끝나지 않았다면, 나중에 돌아와 남은 작업을 할 수 있도록 상태를 보관해야 합니다. JVM에서는 호출마다 지역 변수와 실행에 필요한 정보를 **스택 프레임**에 둡니다. [JVM 프레임](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.6)

**Java**

```java
static long sumRecursive(int[] values, int index) {
    if (index == values.length) {
        return 0;
    }
    return values[index] + sumRecursive(values, index + 1);
}
```

**Python**

```python
def sum_recursive(values, index=0):
    if index == len(values):
        return 0
    return values[index] + sum_recursive(values, index + 1)
```

Python도 아직 끝나지 않은 함수 호출의 상태를 보관하므로 같은 원리로 공간을 분석합니다. 위 코드는 리스트를 잘라 복사하지 않고 같은 리스트와 다음 인덱스를 전달합니다.

`[10, 20, 30]`을 `index = 0`부터 더하면 다음처럼 진행됩니다.

```text
호출: sum(0) → sum(1) → sum(2) → sum(3)
대기: 10 + ?    20 + ?    30 + ?    0 반환
복귀: 60     ←  50     ←  30     ←  0
```

맨 끝에서 `0`을 반환하기 전까지 앞의 호출들은 결과를 기다립니다. 배열은 같은 객체를 공유하지만 호출 프레임은 입력 길이에 비례해 쌓이므로, 시간 `O(N)`, 보조 공간 `O(N)`입니다. 앞의 반복문 버전은 합을 변수 하나에 계속 누적하므로 보조 공간이 `O(1)`이었습니다.

스택 공간은 **전체 호출 횟수가 아니라 동시에 쌓인 최대 호출 깊이**와 프레임당 크기로 판단합니다. 호출이 끝나면 프레임이 제거되기 때문입니다. [재귀 깊이와 공간 분석](https://courses.cis.cornell.edu/courses/cs2110/2025fa/lectures/lec06/)

<details>
<summary>이해 보충: 재귀가 깊거나 객체를 많이 만들면 JVM에서는 어떤 일이 생길까?</summary>

허용된 스택 크기보다 더 큰 스택이 필요하면 `StackOverflowError`가 발생합니다. 기본 스택 크기는 환경과 설정에 따라 달라지므로 ‘항상 1MB’로 외우지 않습니다. 이 오류가 발생했다는 사실만으로 프로세스 전체의 즉시 종료를 뜻하지도 않습니다.

힙에서 필요한 메모리를 확보할 수 없으면 `OutOfMemoryError`가 발생할 수 있습니다. 객체 할당과 보관량 증가는 GC 부담에도 영향을 주지만, 정지 시간은 수집기와 설정, 살아 있는 객체의 양 등에 따라 달라집니다. `O(N)`이라는 표기만으로 메모리 부족이나 GC 정지 시간을 예측할 수는 없습니다. [JVM 스택·힙 명세](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.5)

</details>

### 3-9. 시간과 공간은 어떻게 맞바꿀 수 있을까?

실무 사례의 `HashSet`은 조회를 위해 추가 공간을 쓰는 선택입니다. 목록을 읽어 조회 구조를 만드는 작업을 먼저 해 두고, 이후의 반복 검색을 줄입니다. 이처럼 **메모리를 더 사용해 반복 작업을 줄이거나, 저장량을 줄이는 대신 재계산을 선택하는 관계**를 시간·공간 트레이드오프라고 합니다.

계산 결과를 저장해 같은 계산을 반복하지 않는 **메모이제이션**도 같은 원리입니다. 다만 얼마나 빨라지는지는 중복 계산의 양과 저장할 상태 수에 따라 달라집니다. 저장만 하면 어떤 알고리즘이든 `O(1)`이 되는 것은 아닙니다.

메모리를 줄이는 선택도 있습니다. 데이터를 한 건씩 독립적으로 처리할 수 있다면 `N`건을 전부 보관하는 대신 최대 `B`건씩 읽고 처리한 뒤 버릴 수 있습니다. 결과도 계속 쌓아 두지 않는다는 조건에서 작업 버퍼는 `O(N)` 대신 `O(B)`로 제한됩니다. `B`가 입력과 무관하게 고정되어 있으면 `N`에 대해 `O(1)`입니다.

이때 읽기 요청이 늘어 느려질 수도 있지만, 메모리와 GC 부담이 줄어 빨라질 수도 있습니다. **시간과 공간이 반드시 반대로 움직이는 것은 아닙니다.** 처리 방식과 비용을 보고 판단합니다.

### 3-10. 복잡도를 구한 뒤에도 실제 측정이 필요한 이유

배열을 한 번 훑는 두 코드가 모두 `O(N)`이어도, 하나는 정수 덧셈만 하고 다른 하나는 매번 객체를 만들 수 있습니다. 반복 횟수의 증가율은 같지만 반복 한 번의 비용은 다릅니다.

또한 앞서 배운 것처럼 가까운 주소를 이어 읽으면 캐시에 가져온 데이터를 재사용하기 좋고, JVM은 자주 실행되는 코드를 JIT로 최적화할 수 있습니다. 따라서 **같은 복잡도라고 실제 시간이 같지는 않습니다.** 복잡도는 캐시 적중이나 명령어당 클럭 수도 보장하지 않습니다.

실무에서는 먼저 복잡도로 입력 증가에 취약한 구조를 찾습니다. 이후 실제에 가까운 데이터 크기와 분포로 실행해 시간·메모리를 확인합니다. API에서는 계산 외에도 DB·네트워크 대기와 동시 요청이 영향을 주므로, 알고리즘의 복잡도만으로 응답 시간을 단정하지 않습니다.

<summary>심화: Java 코드의 실행 시간을 비교하려면?</summary>

한 번 실행한 시간을 비교하면 JIT 준비 상태, GC, 다른 작업의 영향을 받기 쉽습니다. 같은 입력 조건에서 반복 측정하고, 처음 실행과 충분히 실행된 상태를 구분합니다. 입력이 커질 때의 변화도 함께 확인합니다.

작은 Java 연산을 비교하는 마이크로벤치마크에는 OpenJDK의 **JMH**를 활용할 수 있습니다. 다만 작은 코드의 측정 결과와 서비스 전체 응답 시간은 서로 다른 대상입니다. [OpenJDK JMH](https://github.com/openjdk/jmh)

</details>
