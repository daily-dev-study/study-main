### 🎯 머릿속에 남겨야 할 핵심 Q&A 2가지

**Q1. 멀티태스킹 환경에서 컨텍스트 스위칭(Context Switching)이 일어날 때, 하드웨어(CPU) 관점에서 정확히 어떤 일이 발생하나요?**
* **A:** OS 스케줄러에 의해 실행 중인 스레드가 교체될 때, CPU는 현재 코어의 상태값(PC, IR, 범용 레지스터 내 중간 계산값 등)을 메모리(TCB)에 모두 백업(Save)하고, 새로운 스레드의 상태를 메모리에서 레지스터로 다시 적재(Restore)합니다. 이 과정에서 연산장치(ALU)는 비즈니스 로직을 전혀 처리하지 못하고 값 복사에만 클럭(시간)을 낭비하게 되며(오버헤드 발생), 잦은 교체는 시스템 처리량을 급감시킵니다.

**Q2. 인텔의 x86(CISC)과 ARM(RISC)은 명령어 처리 방식에서 어떤 차이가 있으며, 왜 현대 클라우드는 ARM 비중을 늘리고 있나요?**
* **A:** CISC는 복잡하고 길이가 제각각인 명령어를 사용하여 제어장치(CU) 회로가 무겁고 발열이 심합니다. 반면 RISC는 명령어를 단순하고 일정한 길이(고정 길이)로 규격화하여 파이프라이닝 효율을 극대화한 아키텍처입니다. 현대 클라우드 데이터센터는 '단일 코어의 절대 속도'보다 '전력 대비 성능(저전력/저발열)'이 훨씬 중요하기 때문에 효율이 압도적인 ARM 기반 프로세서를 적극 도입하고 있습니다.

## 2. 실무 & 코딩테스트 아하! 모먼트 (트러블슈팅 사례)
> CPU 아키텍처의 한계를 모르면 며칠 밤을 새워도 원인을 찾을 수 없는 실제 개발/운영 장애 사례입니다.

### 사례 1. Mac에서 빌드한 도커가 AWS 서버에서 즉사한다? (`exec format error`)
* **상황:** M1/M2 Mac(주니어 개발자 로컬)에서 띄웠을 땐 잘 되던 도커 컨테이너를 AWS EC2(리눅스 서버)에 배포하자마자 `standard_init_linux.go:228: exec user process caused: exec format error` 로그를 뱉고 서버가 죽어버렸다.

* **원인:** 로컬 Mac은 **ARM(RISC)** 기반 CPU이고, 배포 대상인 일반 AWS EC2는 **인텔/AMD의 x86-64(CISC)** 기반 CPU이기 때문이다. x86 CPU의 제어장치가 메모리에서 명령어를 읽어 해독하려 했으나, 0과 1의 비트 패턴 규칙 자체가 ARM 전용이라 알아듣지 못하고 예외를 던진 것이다.

* **💡 해결책:** 도커 빌드 시 대상 CPU 아키텍처를 강제로 명시하여 타깃 제어장치에 맞게 교차 컴파일해야 한다. (`docker buildx build --platform linux/amd64`)

### 사례 2. 스레드를 500개 띄웠더니 서버 전체가 멈췄다 (컨텍스트 스위칭 오버헤드)

* **상황:** 대량의 결제 데이터 연산을 빨리 끝내려고 Java 스레드 풀을 500개(`newFixedThreadPool(500)`)로 돌렸으나 서버가 뻗어버렸다.

* **원인:** 서버의 물리 코어는 4개뿐인데, OS가 500개의 스레드에게 코어를 공평하게 나눠주기 위해 1초에 수만 번씩 코어의 주인을 바꿨기 때문이다. 이때마다 CPU는 위에서 배운 
**'레지스터 값 백업/복원(컨텍스트 스위칭)'** 만 하다가 연산을 할 클럭(시간)을 전부 탕진해 버렸다.
* **💡 해결책:** 암호화나 수학 계산 같은 CPU 연산 중심(CPU-bound) 작업은 스레드 풀 크기를 '물리 코어 수(N) + 1'로 세팅해야 낭비 없이 최고 성능을 낸다.


### 사례 3. 정렬된 배열이 정렬 안 된 배열보다 연산이 3배 빠른 이유

* **상황:** 크기 10만짜리 배열에서 `if (값 > 50)` 인 숫자만 더하는 코드를 짰다. 배열을 `sort()`로 미리 정렬하고 돌렸더니 연산 속도가 3배 이상 빨라졌다.

* **원인:** CPU의 **분기 예측(Branch Prediction)** 기술 때문이다. CPU는 코드를 처리할 때 다음 코드를 미리 컨베이어 벨트(파이프라인)에 올린다. 배열이 뒤죽박죽이면 예측이 계속 틀려 벨트에 올린 명령어를 전부 쓰레기통에 버려야(Flush) 하지만, 정렬이 되어 있으면 `False, False... True, True` 패턴이 명확해 CPU가 다음 명령어를 100% 확률로 명중시켜 초고속으로 처리한다.

## 3. Deep Dive: 하드웨어 밑바닥 원리와 직관적 비유
> 메인 메모리(RAM)는 수동적인 창고일 뿐이다. 메모리에 놓인 0과 1을 실제 행동으로 밀어붙이는 능동적 주체, CPU의 작동 원리를 파헤친다.

### 3-1. CPU 핵심 하드웨어 구조 (일류 요리사의 주방 비유)
CPU 내부의 구조는 **'초고속 자동화 주방에서 일하는 일류 요리사'** 와 같다.

* **PC (프로그램 카운터):** 다음에 실행할 주소를 보관. 
    - 👨‍🍳 **요리사의 번호판** *"다음 가져올 레시피는 104번이다!"*

* **MAR (메모리 주소 레지스터, Memory Address Register):** RAM에서 읽거나 쓸 대상의 '번지수(주소)'만 보관. (주소 버스와 연결됨)
  * 👨‍🍳 **주소 쪽지:** 주방 보조에게 *"창고 104번 칸으로 가라!"* 하고 위치만 적어 넘기는 쪽지.

* **MBR (메모리 버퍼 레지스터, Memory Buffer Register):** RAM에서 방금 꺼내왔거나 저장할 '실제 데이터/기계어'를 임시 보관. (데이터 버스와 연결됨)
  * 👨‍🍳 **배식 쟁반:** 주방 보조가 104번 칸에서 꺼내온 실제 양파(데이터)나 레시피 카드(명령어)를 담아 들고 오는 쟁반.

> 💡 **의문: 그냥 레지스터 하나에 주소랑 데이터를 다 담으면 안 되나요? 왜 굳이 MAR과 MBR 두 개로 쪼개 놓았죠?**
> * **해답:** 하드웨어의 물리적인 '통로(Bus)'가 나뉘어 있기 때문이다. 메인보드에는 위치를 찾는 선(주소 버스)과 실제 데이터를 나르는 선(데이터 버스)이 물리적으로 분리되어 있다. 통로가 2개이니, CPU 쪽에서도 각 통로와 1:1로 직접 연결될 출입구(인터페이스) 역할을 하는 레지스터를 2개로 분리해 두어야 병목 현상 없이 초고속으로 통신할 수 있다.

> 💡 **MAR과 MBR의 완벽한 티키타카 (협력 과정)** <br>
> 메모리에서 명령어를 가져오는 '인출(Fetch)' 단계를 보면 이 둘의 협업이 명확하게 보인다.
> 1. **PC ➡️ MAR:** PC가 "다음은 100번지다!"라고 하면, 100이라는 숫자가 **MAR(주소 쪽지)** 에 복사된다.
> 2. **MAR ➡️ RAM (주소 버스):** MAR이 주소 버스를 통해 메모리에게 "100번지 창고 열어!"라고 신호를 보낸다.
> 3. **RAM ➡️ MBR (데이터 버스):** 메모리가 100번지 창고를 열어보니 `ADD` 명령어가 있다. 이를 데이터 버스에 태워 **MBR(쟁반)** 에 얹어준다.
> 4. **MBR ➡️ IR:** CPU는 쟁반(MBR)에 놓인 `ADD` 명령어를 집어서, 요리사 눈앞의 조리대 클립보드인 **IR(명령어 레지스터)** 에 딱 꽂아두고 해독을 시작한다.

* **IR (명령어 레지스터):** 메모리에서 갓 가져온 명령어를 보관. 
    - 👨‍🍳 **조리대 앞 클립보드** *"지금 눈앞에 꽂아둔 레시피 카드"*

* **CU (제어장치):** 기계어를 해독하고 제어 신호를 쏨.
    - 👨‍🍳 **요리사의 두뇌** *"이건 양파를 썰라는 암호군. 칼을 움직여라!"*

* **ALU (연산장치):** 실제 산술(+,-) 및 논리(비교) 연산 수행. 
    - 👨‍🍳 **칼과 프라이팬**

* **범용 레지스터 (AX, BX 등):** 연산 데이터를 임시로 담아두는 CPU 내장 초고속 메모리. 
    - 👨‍🍳 **도마 바로 옆 작은 접시들** *"조리 중간에 썬 양파를 0.1초 만에 담아뒀다 다시 집어 드는 곳"*

### 3-2. 명령어 사이클 4단계와 파이프라이닝
CPU가 코드 한 줄(`ADD AX, BX`)을 처리하는 과정은 다음과 같다.

1. **인출 (Fetch):** 레시피 가져오기 
    * **PC(번호판)** ➡️ **MAR(주소 쪽지)** ➡️ **RAM(창고)** ➡️ **MBR(쟁반)** ➡️ **IR(클립보드)** 순서로, <br>
    다음 실행할 명령어를 메모리에서 가져와 요리사 눈앞에 딱 꽂아두는 단계다.
2. **해석 (Decode):** CU(제어장치)가 레시피 판독하기
    * 요리사의 두뇌 역할을 하는 **CU(Control Unit)** 가 클립보드에 꽂힌 0과 1의 비트를 쓱 읽고, <br>
    **"아! 이건 더하기(ADD) 명령이구나!"** 라고 해독한 뒤 각 부품에 작업 지시(제어 신호)를 내린다.
3. **실행 (Execute):** ALU가 실제 덧셈 수행하기
    * 칼과 프라이팬 역할을 하는 **ALU(Arithmetic Logic Unit)** 가 CU의 지시에 따라 실제 덧셈이나 비교 연산을 묵묵히 수행한다.
4. **기록 (Write-back):** 결과를 범용 레지스터(접시)에 담기
    * ALU가 계산을 마친 덧셈 결과물을 도마 옆의 작은 접시인 **범용 레지스터(AX)** 에 덮어쓰면서 하나의 사이클이 끝난다.

> 💡 **의문: 이 4단계가 다 끝나길 기다렸다가 다음 코드를 실행하면 너무 느리지 않을까?**
> * **해답:** 그래서 현대 CPU는 **파이프라이닝(Pipelining)** 기술을 쓴다. 요리사가 1번 요리를 '프라이팬에서 볶는(실행)' 동안 멍하니 서 있는 게 아니라, 동시에 2번 레시피를 '읽고(해석)', 3번 재료를 냉장고에서 '꺼내온다(인출)'. <br>
> 즉, 컨베이어 벨트처럼 여러 명령어의 단계들을 겹쳐서 동시에 실행해 성능을 극대화하는 하드웨어 설계 기법이다.

### 3-3. 클럭, 코어, 그리고 하이퍼스레딩
> 💡 **실무 의문: 백엔드 개발자가 클럭과 코어 같은 하드웨어 스펙까지 알아야 할까?**
> * **해답:** AWS나 클라우드에서 서버(EC2)를 임대할 때 사양표에 적힌 `2 vCPU`, `3.0GHz`의 진짜 의미를 해독하기 위해서다. 하드웨어의 물리적 한계를 모르면 소프트웨어 스레드를 무작정 늘리다가 서버를 터뜨리는 실수를 하게 된다.

* **클럭 (Clock, GHz)** 
    - **개념:** CPU 내부의 진동자가 만드는 전기적 박자.
  * 👨‍🍳 **주방의 메트로놈:** `3.0 GHz`는 1초에 30억 번의 "째깍" 박자가 울린다는 뜻이다. CPU의 부품들은 이 박자에 맞춰 단 1비트의 엇갈림도 없이 파이프라인(컨베이어 벨트)의 다음 단계로 데이터를 넘긴다. 클럭이 높을수록 요리사의 손놀림이 빨라진다.

* **코어 (Core)** 
    * **개념:** 독립적으로 요리(명령어 사이클)를 처음부터 끝까지 해낼 수 있는 완전한 물리적 주방 세트 1개(CU+ALU+레지스터). 
  * 👨‍🍳 **실제 요리사의 인원수:** 코어가 4개(Quad-core)면, 1초에 진짜로 4개의 요리(스레드)를 동시에 볶을 수 있다.

* **하이퍼스레딩 (Hyper-Threading / 논리 코어)** 
    - **개념:** 물리적인 코어(연산 장치)는 1개인데, 그 안에 상태를 저장하는 레지스터(도마와 클립보드)만 2세트로 복제하여 운영체제가 코어를 2개로 인식하게 만드는 기술.
    - 👨‍🍳 **비유:** 요리사(ALU)가 1번 요리를 하다가 창고(RAM)에서 재료가 오기를 기다려야 할 때 멍하니 서 있지 않고, 즉시 옆 도마로 넘어가 2번 요리 재료를 썰게 만드는 쥐어짜기 방식이다.

> 💡 **의문: AWS 사양표를 보면 '물리 코어는 1개인데 vCPU는 2개'라고 홍보한다. 코어를 2개인 것처럼 속이는 이유가 무엇이며, 성능도 진짜 2배가 될까?**
> * **해석과 해답:** OS(운영체제)는 하드웨어를 바라볼 때 '레지스터 세트(도마와 클립보드)'가 2개 있으면 "아하! 요리사(코어)가 2명이구나!"라고 착각하여 두 가지 일을 동시에 배분한다. 클라우드에서 말하는 `vCPU(논리 코어)`가 바로 이 가짜 코어를 의미한다. 
>
> * 하지만 실제로 연산을 수행하는 칼(ALU)은 결국 1개뿐이므로, 진짜 물리 코어가 2개인 컴퓨터처럼 성능이 딱 2배가 되지는 않는다. (대기 시간을 줄여 대략 20~30% 정도의 효율 향상만 있다.)

### 3-4. CISC vs RISC (아키텍처 철학의 대립과 하드웨어의 진화)
> 💡 **실무 의문: 백엔드 개발자가 왜 이 두 철학의 대립까지 알아야 할까?** 
> * **이유:** 최근 넷플릭스나 배달의민족 같은 거대 IT 기업들이 AWS 서버 인프라를 기존 인텔(CISC) 방식에서 ARM(RISC) 기반 프로세서로 대거 교체하고 있기 때문이다. 왜 굳이 서버 칩을 바꾸는지, 그 밑바탕을 이해하려면 이 두 철학을 알아야 한다.

이 둘은 **"CPU에게 일을 시키는 방식(명령어)"** 에 대한 공학자들의 철학 차이에서 출발했다.

**1. CISC (Complex Instruction Set Computer): 인텔 x86, AMD**
* **철학:** *"소프트웨어(컴파일러)를 괴롭히지 마! 하드웨어(CPU)가 똑똑하게 다 알아서 해줄게. 복잡한 명령어 한 방으로 끝내자!"*

* 👨‍🍳 **비유 (밀키트 주문):** 점장(프로그래머)이 요리사(CPU)에게 **"김치찌개 끓여!"** 라는 복잡한 명령어 딱 1개를 던진다. 그러면 요리사의 두뇌(CU)가 알아서 <u>'김치 꺼내기 => 물 끓이기 => 고기 넣기'</u>를 전부 알아서 해석하고 실행한다.

* **특징과 한계:** 명령어 길이가 1~15바이트로 제각각(가변 길이)이다. 똑똑한 요리사를 만들려다 보니 칩 내부의 제어장치(CU) 회로가 너무 비대해져서 전기를 많이 먹고 **발열이 극심**하다. 명령어가 끝나는 시간이 제각각이라 파이프라이닝(컨베이어 벨트)을 돌리기가 매우 까다롭다.

**2. RISC (Reduced Instruction Set Computer): ARM, 애플 M시리즈, AWS Graviton**
* **철학:** *"CPU 회로를 복잡하게 만들지 마! 명령어는 무조건 단순하게(Reduced) 규격화하고, 대신 컨베이어 벨트를 미친 듯이 빨리 돌리자!"*

* 👨‍🍳 **비유 (서브웨이 공장):** 점장이 "김치찌개 끓여!" 같은 복잡한 지시를 내릴 수 없다. 대신 **"1. 냄비 가져와", "2. 물 넣어", "3. 끓여"** 처럼 아주 단순한 명령어 3개를 순서대로 준다. 요리사(CU)는 멍청해도 된다. 들어오는 단순 명령을 기계적으로 처리하면 된다.

* **특징과 장점:** 명령어 길이가 무조건 4바이트(고정 길이)로 똑같다. 구조가 단순해 톱니바퀴 맞물리듯 **파이프라이닝(컨베이어 벨트)을 쌩쌩 돌리기에 최적화**되어 있다. 회로가 얇아 발열이 적고 전력 효율이 압도적이라 스마트폰뿐 아니라 현대 백엔드 클라우드 데이터센터까지 무서운 속도로 장악하고 있다.

> 💡 **아하! 모먼트: 기술 면접 단골 질문 - Load/Store 아키텍처**
> 면접관이 둘의 기술적 차이를 묻는다면 **'메모리 접근 방식'**을 답해야 한다.
> * **CISC의 덧셈 (`ADD [메모리 100번지], 5`):** CISC는 복잡한 일을 한 번에 하므로, 메모리 100번지에 있는 값에 직접 5를 더하는 것이 허용된다.
> * **RISC의 덧셈 (`LOAD` ➡️ `ADD` ➡️ `STORE`):** RISC는 메모리에 직접 연산하는 걸 철저히 금지한다. 오직 **LOAD(메모리에서 레지스터로 가져오기)**와 **STORE(레지스터에서 메모리로 저장하기)** 명령어만 메모리에 접근할 수 있으며, 덧셈(ADD) 자체는 무조건 CPU 내부의 레지스터 안에서만 수행해야 한다. 이렇게 역할을 극단적으로 분리해야 컨베이어 벨트가 꼬이지 않고 돌아가기 때문이다.
