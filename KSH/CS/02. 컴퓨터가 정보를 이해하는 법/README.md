# 컴퓨터가 정보를 이해하는 법 (0과 1의 세계)

## 1. 면접 직전 1분 요약 노트 (비법 노트)
> 면접 전날, 이 구역의 핵심 Q&A만 빠르게 훑고 들어갑니다.

* **Q. CPU의 연산장치(ALU)는 뺄셈을 할 때 왜 별도의 감산기(뺄셈 회로)를 두지 않고, 가산기(덧셈기)만 사용하나요?**
  * **A:** 하드웨어 칩셋의 공간 낭비와 발열, 단가를 줄이기 위해서입니다. 대신 소프트웨어적으로 음수를 **'2의 보수(Two's Complement)'** 형태로 변환하여 덧셈기에 넣으면, 최상위 비트의 올림수(Carry)가 자연스럽게 버려지면서 뺄셈과 완벽히 동일한 결과가 나오는 수학적 원리를 활용합니다.

* **Q. 자바(Java)나 파이썬에서 금융 결제 금액을 다룰 때 `double`이나 `float`을 쓰면 안 되는 이유는 무엇인가요?**
  * **A:** 컴퓨터가 실수를 저장하는 **IEEE 754 부동소수점 방식**의 물리적 한계 때문입니다. 10진수 실수를 2진수로 변환하면 무한 순환 소수가 되는데, 메모리의 가수부 비트(23~52비트)는 공간이 한정되어 있어 초과하는 뒷자리를 강제로 잘라냅니다. 이로 인해 필연적인 '근사 오차'가 발생하여 장부 불일치가 생기므로, 실무에서는 자바의 `BigDecimal` 등을 사용하여 오차를 원천 차단해야 합니다.

## 2. 실무 & 코딩테스트 아하! 모먼트 (트러블슈팅 사례)
> 단순 이론이 아니라, 0과 1의 하드웨어적 한계 때문에 실제 서비스에서 터지는 치명적인 버그들입니다.

### 사례 1. 유튜브 강남스타일 조회수 마이너스(-21억) 사건 (Integer Overflow)

* **상황:** 과거 유튜브에서 강남스타일 조회수가 21억 4천만 뷰를 넘어서는 순간, 조회수가 갑자기 `-2147483648`로 변해버린 실제 사건입니다.
* **원인:** 조회수를 저장하던 자료형이 32비트 부호 있는 정수(`signed int`)였기 때문입니다. 이 자료형은 맨 앞 1비트(MSB)를 '부호(0이면 양수, 1이면 음수)'를 나타내는 데 사용합니다. 
* **결과:** 양수의 최대치인 21억 4천만(`0111 1111...`)에서 1조회수가 더해지는 순간, 비트가 `1000 0000...`으로 뒤집히게 됩니다. 시스템은 2의 보수 체계에 따라 맨 앞의 1을 보고 이를 가장 작은 음수인 마이너스 21억으로 해석해 버렸고, 결국 대형 버그로 이어졌습니다. (현재 유튜브는 이를 64비트로 업그레이드하여 해결했습니다.)


### 사례 2. DB에 한글 4글자 넣었더니 터지는 에러 (문자 인코딩 설정)

* **상황:** DB에 사용자 닉네임 컬럼을 `VARCHAR(10)`으로 넉넉하게 설정했습니다. 영문 아이디 "abcdefghij"(10글자)는 잘 들어가는데, 한글 닉네임 "홍길동입니다"(6글자)를 넣자 에러가 발생합니다.
* **원인:** 가변 길이 인코딩인 **UTF-8에서 한글은 1글자가 3바이트**를 차지하기 때문입니다. 만약 DB 엔진 설정이 `VARCHAR` 길이를 글자 수(Character)가 아닌 바이트(Byte) 제한으로 인식하고 있다면, 한글 3글자(9바이트)까지만 정상 저장되고 4글자(12바이트)부터는 10바이트 디스크 블록을 초과해 튕겨 나가게 됩니다.

## 3. Deep Dive: 하드웨어 밑바닥 원리와 직관적 비유
> 우리가 짠 코드가 0과 1로 변환되어 물리적으로 어떻게 처리되는지 파헤친 상세 기록입니다.

우리 코드가 컴퓨터 내부의 구리선 위를 달릴 때는 알파벳이나 숫자가 아니라, 오직 **"전기가 흐른다(High: 약 3.3V) / 안 흐른다(Low: 0V)"** 두 가지 물리적 현상만 존재합니다. </br>
이 전기 신호를 컴퓨터는 **1과 0(Bit)**으로 인식합니다. 0과 1밖에 모르는 멍청한 바리스타(CPU)는 인간이 미리 쥐여준 **'모스 부호 번역 책(인코딩 규약)'**을 대조해가며 복잡한 명령을 오차 없이 수행해 냅니다.


### 3-1. 바이트(Byte) 주소 체계의 비밀 (모래알 비유)

* 📖 **실제 의미:** 하드웨어 메모리 공간에 번지수(Address)를 할당하는 최소 단위는 1비트가 아니라 8비트를 묶은 1바이트(Byte)입니다.

* ☕ **직관적 비유 (모래알과 주소록):**
  * 데이터의 최소 단위인 비트(Bit)를 '모래알'이라고 해보겠습니다. <br>
  16GB짜리 거대한 모래사장(RAM)에 있는 모래알 1개 1개마다 고유 주소(0x00번지, 0x01번지...)를 다 매기면 어떻게 될까요? <br>
  모래알 위치를 기록할 '주소록(주소 버스와 포인터 변수의 크기)'이 천문학적으로 두꺼워져서 시스템이 감당하지 못합니다.
  
  * 그래서 공학자들은 영문자 1개를 담기 딱 좋은 사이즈인 **'모래알 8개를 묶어 1바이트 상자'** 로 규격화했습니다. <br>
  그리고 메모리 주소는 무조건 이 '상자' 단위로만 매기도록 하드웨어를 굳혀버렸습니다.

> **🔥 [실무 트러블 슈팅]: 100만 명의 `boolean` 데이터와 메모리 폭발 현상**
> * **상황:** 출석 체크 앱에서 100만 명의 유저 출석 여부(True/False)를 `boolean[]` 배열에 담았습니다. 100만 비트니까 용량이 대략 125KB 정도 될 줄 알았는데, 서버 메모리가 1MB 넘게 훅 날아갔습니다.
> * **원인:** 우리가 방금 배운 '바이트 단위 어드레싱' 때문입니다. CPU는 1비트 단위로 주소를 찾지 못하므로, 자바(Java)는 고작 1비트짜리 `True/False`를 저장할 때도 최소 주소 단위인 **'1바이트 상자'를 통째로 할당**해 버립니다. 즉, 7비트가 낭비되는 것입니다.
> * **해결책:** 대규모 불리언 연산을 할 때는 메모리를 극적으로 아껴주는 `BitSet`(자바) 같은 특수 자료구조를 써야 낭비 없이 1비트씩 꽉꽉 채워 쓸 수 있습니다.
>
> **💡 [실무 해결책]**
> * **비트 플래그 & `BitSet` 활용:** 대규모 불리언 연산을 할 때는 메모리를 극적으로 아껴주는 자바의 `BitSet` 같은 특수 자료구조를 씁니다. 이는 내부적으로 `long` 배열을 사용해 비트 단위 연산(비트 마스킹)을 수행하므로, 낭비 없이 1비트씩 꽉꽉 채워 메모리 사용량을 1/8로 획기적으로 줄일 수 있습니다.

### 3-2. 음수의 표현 (2의 보수와 좁은 카페 비유)

* 📖 **실제 의미:** CPU는 뺄셈 회로를 추가하지 않고 덧셈 회로(가산기)만으로 뺄셈을 처리하기 위해, <u>음수의 모든 비트를 뒤집고 1을 더하는 '2의 보수법'</u>을 씁니다.

* ☕ **직관적 비유:** 카페가 너무 좁고 더워서 뺄셈 전용 기계(감산기)를 아예 버렸습니다. 대신 천재 공학자들이 **"음수 숫자를 적당히 뒤집어서 덧셈 기계에 넣으면 자연스럽게 뺄셈이 툭 튀어나오게"** 수학적 꼼수를 부렸습니다.

  ```text
  [ 5 - 5 를 덧셈 기계(8비트 상자)로 계산하는 마법 같은 과정 ]
  1. 양수 5 = 0000 0101
  2. 음수 -5 만들기 (2의 보수법) = 0과 1을 전부 뒤집고 끝에 1을 더함 👉 1111 1011
  
  3. 이제 덧셈 기계에 넣고 덧셈을 수행합니다.
       0000 0101  (5)
    +  1111 1011  (-5)
    ------------------
     (1)0000 0000 
  
  4. 더해보니 맨 앞자리로 계속 1이 넘어가면서(올림수) 9자리 숫자가 되었습니다.
  5. 하지만 우리는 규격화된 '8칸짜리 상자'만 쓰기 때문에, 공간을 뚫고 나간 맨 앞의 '1'은 허공으로 떨어져 하드웨어적으로 자연스럽게 버려집니다.
  6. 결과적으로 상자에 남은 숫자는 완벽한 '0000 0000 (0)'이 됩니다.
  ```

> **🔥 [실무 트러블 슈팅]: `Math.abs()`의 배신 (절댓값이 음수로 나오는 버그)**
> * **상황:** 마이너스 금액이 들어오면 무조건 양수로 바꾸기 위해 절댓값 함수 `Math.abs(amount)`를 썼습니다. 그런데 `-2147483648` 이라는 값이 들어오자, 절댓값을 씌웠는데도 여전히 `-2147483648` (음수)가 나오는 치명적 버그가 터졌습니다.
> * **원인:** 2의 보수법이 가진 기형적인 특징 때문입니다. 32비트 정수 공간에서 0이 한자리를 차지하다 보니, 양수는 `0`부터 `2147483647`까지, 음수는 `-1`부터 `-2147483648`까지 존재합니다. 즉, **음수가 양수보다 딱 1개 더 많습니다.**
> * **결과:** 가장 작은 음수인 `-2147483648`은 짝이 맞는 양수(+2147483648)가 존재하지 않아서 비트를 뒤집어도 양수로 변환되지 못하고 그대로 음수를 반환해 버리는 대형 사고가 납니다.
>
> **💡 [실무 해결책 4가지]** <br>
> 이런 '소리 없는 에러'를 막기 위해 실무에서는 다음 방법들을 씁니다.
> 1. **더 큰 상자로 옮기기 (Upcasting):** 아예 64비트(long) 상자로 먼저 옮긴 뒤에 절댓값을 씌웁니다. => `Math.abs((long) amount)`
> 2. **안전벨트 함수 사용 (Fail-Fast):** Java 8부터 추가된 `Math.absExact(amount)`를 쓰면, 오버플로우 감지 시 즉시 에러(`ArithmeticException`)를 터뜨려줍니다. (장부가 꼬이는 것보단 시스템이 소리치며 죽는 게 낫습니다.)
> 3. **검문소 세우기 (Guard Clause):** 로직 최상단에 `if (amount == Integer.MIN_VALUE)` 조건을 걸어 직접 예외 처리(방어 로직)를 던집니다.
> 4. **근본적 원인 제거:** 금융권에서 '돈'을 다룰 때는 애초에 `int`를 쓰지 않고, 메모리 한계와 오차가 없는 `BigDecimal` 객체를 사용해 오버플로우를 원천 차단합니다.

### 3-3. 실수의 표현 (IEEE 754와 꼬리 자르기 비유)
* 📖 **실제 의미:** 컴퓨터는 소수점 위치를 고정하지 않고 <u>**부호(1비트)+지수부(8비트)+가수부(23비트)**</u>로 나누어 저장하는 부동소수점 방식을 씁니다. <br>
이때 10진수를 2진수로 변환 시 발생하는 무한 순환 소수 때문에 필연적인 근사 오차가 생깁니다.

* ☕ **직관적 비유:**
    - 32비트 메모리 중 유효 숫자를 담는 '가수부' 상자는 딱 23칸뿐입니다. 우리가 흔히 쓰는 10진수 0.1을 2진수로 바꾸면 0.0001100110011... 처럼 끝이 없는 **무한 순환 소수**가 되어버립니다.

    - 이 무한한 꼬리를 23칸짜리 상자에 다 담을 수 없으니, 컴퓨터는 **나머지 꼬리를 가위로 싹둑 잘라버립니다.** (반올림 처리)

    - 결국 진짜 0.1이 아니라 꼬리가 잘린 가짜 근사치 값(예: 0.10000000000000002)이 저장되며, 이 오차가 쌓여 대형 금융 사고를 유발합니다.

> **🔥 [실무 트러블 슈팅]: 영원히 끝나지 않는 무한 루프 버그**
> * **상황:** 게이지가 0에서 1.0까지 차오르는 기능을 구현하기 위해 아래와 같은 코드를 짰습니다.
>   `for (double d = 0.0; d != 1.0; d += 0.1) { ... }`
> * **원인:** 인간의 눈에는 0.1씩 열 번 더하면 정확히 1.0이 될 것 같지만, 컴퓨터의 `d`에는 꼬리가 잘린 가짜 숫자(근사치)가 더해지고 있습니다.
> * **결과:** 루프를 열 번 돌았을 때 `d`의 값은 `0.9999999999999999`가 되어 버립니다. 따라서 조건문(`d != 1.0`)이 참(True)으로 판정되어, 루프가 종료되지 않고 서버가 죽을 때까지 무한 루프를 돌게 됩니다. (실수끼리는 절대 `==`나 `!=`로 비교하면 안 됩니다.)
>
> **💡 [실무 해결책]**
> 1. **정수로 치환해서 연산:** 소수점 연산을 피하기 위해 반복문은 무조건 정수로 돌리고, 내부에서 나눗셈을 합니다. => `for (int i = 0; i < 10; i++) { double d = i / 10.0; }`
> 2. **엡실론(Epsilon) 비교:** 실수끼리는 절대 동등 비교(==, !=)를 하면 안 됩니다. 두 값의 차이가 아주 미세한 기준값(예: 1e-9)보다 작은지를 확인하여 같다고 판정해야 합니다. => `if (Math.abs(d - 1.0) < 1e-9)`

### 3-4. 문자의 표현 (UTF-8과 고무줄 상자 비유)

* 📖 **실제 의미:** 과거 7비트 아스키(ASCII) 코드의 한계를 넘어 전 세계 언어(유니코드)를 표현하기 위해 도입된 '가변 길이 문자 인코딩' 표준입니다.

* ☕ **직관적 비유:**

    - 예전에는 무조건 똑같은 고정 크기의 상자에 글자를 담았습니다. 그러다 보니 영어(알파벳)를 담을 땐 공간이 남아돌아 메모리 낭비가 심했습니다.

    - 그래서 **UTF-8은 글자의 종류에 따라 상자 크기를 고무줄처럼 쭈욱 늘려 쓰는 혁신**을 가져왔습니다. 단순한 **영어와 숫자**는 작은 1바이트 상자에 쏙 넣고, 복잡한 **한글이나 한자**는 3바이트로 늘려서 넣으며, 화려한 이모지(😀)는 4바이트 상자로 쭈욱 늘려서 담아 메모리를 극한으로 아끼면서 모든 언어를 호환하게 되었습니다.

> **🔥 [실무 트러블 슈팅]: 게시판에 이모지를 넣었더니 DB가 터졌다 (`utf8` vs `utf8mb4`)**
> * **상황:** 백엔드를 처음 배울 때 MySQL 데이터베이스 인코딩 설정을 그냥 `utf8`로 세팅했습니다. 나중에 사용자가 게시글 제목에 이모지(🥰)를 입력하고 저장 버튼을 누르자 DB 에러가 발생하며 서버가 뻗었습니다.
> * **원인:** MySQL의 기본 `utf8` 설정은 고무줄 상자를 **최대 3바이트까지만** 늘리도록 막아둔 반쪽짜리 가짜 UTF-8이기 때문입니다. 앞서 말했듯 이모지는 4바이트 상자가 필요한데, 상자가 3바이트에서 안 늘어나니 데이터가 터져버린 것입니다.
> * **해결책:** 요즘 백엔드 실무에서 MySQL을 세팅할 때는 무조건 4바이트까지 온전히 지원하는 **`utf8mb4`** 인코딩 방식을 기본값으로 설정해야 이모지 저장 버그를 막을 수 있습니다.
>
> **💡 [실무 해결책]**
> 1. **DB 기본 캐릭터셋 변경:** 백엔드 실무에서 MySQL을 세팅할 때는 무조건 4바이트까지 온전히 지원하는 utf8mb4 인코딩 방식과 utf8mb4_unicode_ci 콜레이션(Collation)을 기본값으로 설정해야 이모지 저장 버그를 완벽하게 막을 수 있습니다.
> 2. **애플리케이션 단의 방어:** 만약 이미 운영 중이라 DB 설정을 바꿀 수 없다면, 정규표현식을 사용해 백엔드 서버(Spring Boot 등) 단에서 저장 전 이모지만 필터링해서 빈 문자열로 치환하는 우회 방식을 사용해야 합니다.
