# [M2-4] 출입구를 통제하는 선형 구조 — 스택(Stack), 큐(Queue), 덱(Deque)

## 1. 면접 핵심 Q&A

### Q1. 스택(Stack), 큐(Queue), 덱(Deque)의 구조적 차이는 무엇이며, 컴퓨터 시스템 내부에서는 각각 어디에 사용되는가?
배열이나 연결 리스트가 어디서든 데이터를 넣고 뺄 수 있는 무제한 개방형 그릇이라면, **스택**, **큐**, **덱** 은 시스템의 실행 순서와 흐름을 안전하게 통제하기 위해 **데이터의 출입구 규칙을 엄격하게 제한한 추상 자료형(ADT, Abstract Data Type)** 이다.

* **스택 (Stack — LIFO, 후입선출)** : 한쪽 끝(**Top**)에서만 데이터를 넣고(**Push**) 뺄(**Pop**) 수 있는 구조이다. 가장 나중에 들어온 데이터가 가장 먼저 나가므로, 컴퓨터 시스템에서는 **함수의 호출과 복귀 주소를 관리하는 콜 스택(Call Stack)**, 수식 계산, 브라우저 뒤로 가기(Undo) 히스토리에 사용된다.
* **큐 (Queue — FIFO, 선입선출)** : 뒤(**Rear/Tail**)로만 데이터가 들어오고(**Offer/Enqueue**), 앞(**Front/Head**)으로만 데이터가 나가는(**Poll/Dequeue**) 공정한 대기열 구조이다. 요청을 보내는 **생산자(Producer)와 처리하는 소비자(Consumer) 사이의 속도 차이를 완충하는 모든 버퍼(Buffer)**, 웹 서버 스레드 풀의 작업 대기열, OS의 CPU 스케줄링 대기열, 메시지 큐(Kafka, RabbitMQ)의 근간이 된다.
* **덱 (Deque, Double-Ended Queue)** : 앞(**Front**)과 뒤(**Rear**) 양쪽 끝 모두에서 데이터를 넣고 뺄 수 있는 양방향 구조이다. 한쪽 문만 쓰면 **스택** 이 되고, 한쪽으로 넣고 반대쪽으로 빼면 **큐** 가 되는 만능 구조로, 실무에서는 멀티스레드 환경의 **작업 훔치기(Work-Stealing, Java `ForkJoinPool`)** 알고리즘이나 슬라이딩 윈도우 최적화에 핵심적으로 사용된다.

### Q2. Java에서 스택(LIFO)이나 큐(FIFO)를 구현할 때 레거시 `java.util.Stack` 및 `LinkedList` 대신 `ArrayDeque`을 표준으로 사용해야 하는 이유는 무엇인가?
Java 공식 문서(Javadoc)에서도 스택과 큐 구현 시 **`ArrayDeque`** 을 1순위로 권장하며, 그 이유는 **설계 결함 방지**, **동기화(Lock) 오버헤드 제거**, **GC 부하 및 CPU 캐시 효율** 세 가지로 요약된다.

1. **`java.util.Stack`의 치명적 단점 (Vector 상속과 모니터 락)** :
   * **불필요한 동기화 오버헤드** : `Stack`은 Java 1.0 시절의 `Vector` 클래스를 상속받아 만들어졌기 때문에, 모든 메서드(`push`, `pop`)에 **`synchronized` (모니터 락)** 가 걸려 있다. 단일 스레드가 혼자 쓰는 상황에서도 매번 자물쇠를 잠그고 푸는 무거운 비용이 발생해 성능이 크게 떨어진다.
   * **LIFO 캡슐화 파괴** : `Vector`의 메서드를 그대로 물려받아 `stack.add(0, item)`이나 `stack.get(2)`처럼 **스택의 바닥이나 중간 데이터를 마음대로 조작할 수 있는 객체지향 설계 결함** 을 안고 있다.
2. **`LinkedList` 대비 `ArrayDeque`의 압도적 우위** :
   * `LinkedList`는 데이터를 넣고 뺄 때마다 24바이트짜리 `Node` 포장지 객체를 매번 힙(Heap) 메모리에 새로 생성하고 버리므로 **GC(가비지 컬렉션) 쓰레기가 대량으로 발생** 하고, 메모리가 흩어져 있어 CPU 캐시 미스가 잦다.
   * 반면 `ArrayDeque`은 내부적으로 **원형 배열(Circular Array)** 슬롯을 재사용하고 `head`, `tail` 인덱스 번호만 회전시키므로, **일회용 노드 객체 생성(GC 부하)이 0** 이며 연속된 메모리 덕분에 **CPU 캐시 공간 지역성이 극대화** 된다.

| 비교 항목 | `java.util.Stack` (레거시) | `ArrayDeque` (원형 동적 배열) | `LinkedList` (이중 연결 리스트) | `ArrayBlockingQueue` (동시성 큐) |
| :--- | :--- | :--- | :--- | :--- |
| **내부 물리 구조** | `Vector` 상속 (연속 배열) | **원형 동적 배열** (2의 거듭제곱 크기) | 이중 연결 리스트 (`Node` 객체 연결) | 고정 크기 원형 배열 + `ReentrantLock` |
| **양 끝 삽입 / 삭제** | 맨 뒤만 분할 상환 **O(1)** | **양 끝 모두 분할 상환 O(1)** | **양 끝 모두 O(1)** | 양 끝/단방향 **O(1)** (락 대기 포함) |
| **스레드 안전성 (동기화)** | 모든 메서드 `synchronized` 강제 | 미지원 (단일 스레드 속도 극대화) | 미지원 (단일 스레드용) | **Thread-Safe** (멀티스레드 공유용) |
| **GC 및 메모리 오버헤드** | 낮음 (배열 참조 4B) | **최저** (기존 배열 슬롯 재사용, 노드 생성 0) | **높음** (삽입/삭제마다 24B `Node` 생성·폐기) | 낮음 (초기 고정 배열 슬롯 재사용) |
| **CPU 캐시 지역성** | 우수 | **최상** (연속 메모리 순회) | **최악** (포인터 체이싱 발생) | 우수 |
| **실무 권장 여부** | **사용 금지** (Java 1.0 유물) | **단일 스레드 스택/큐/덱 표준 1순위** | 큐/스택 용도로 비권장 | **스레드 풀 / 생산자-소비자 큐 표준** |

### Q3. 스레드 풀(Thread Pool) 앞단에 작업 큐(Queue)를 둘 때, 크기 제한이 없는 무제한 큐(Unbounded Queue)를 사용하면 어떤 장애가 발생하는가?
웹 서버에서 비동기 작업을 처리할 때 `Executors.newFixedThreadPool(N)`처럼 대기열 크기 제한이 없는 **무제한 큐(Unbounded Queue, 최대 약 21억 개 수용)** 를 사용하면, 외부 API 지연이나 트래픽 폭주로 인해 **소비자(스레드)의 처리 속도보다 생산자(요청)의 유입 속도가 빨라지는 순간 큐에 작업 객체가 끝없이 쌓여 JVM 힙 메모리가 고갈되는 `OutOfMemoryError(OOM)`로 서버 전체가 다운** 된다.

따라서 실무 운영 환경에서는 반드시 **`ArrayBlockingQueue`** 처럼 **최대 용량이 제한된 큐(Bounded Queue)** 를 사용하여 메모리 상한선을 물리적으로 방어하고, 큐가 꽉 찼을 때 요청을 거절하거나 유입 속도를 늦추는 **배압(Backpressure) 및 거절 정책(Rejection Policy)** 을 함께 설계해야 한다.

## 2. 실무 사례 (배경지식 빌드업 & 상세 해부)

실무 사례를 완벽히 이해하기 위해, 아직 다루지 않은 **JVM 메모리와 멀티스레드 핵심 배경지식 5가지** 를 먼저 직관적으로 정리한다.

> **💡 [사전 빌드업] 사례 이해를 위한 5가지 핵심 배경지식**
>
> 1. **JVM 메모리 (Stack 영역 vs Heap 영역)** :
>    * 자바 프로그램이 OS로부터 할당받아 사용하는 메모리 작업실이다. 크게 두 공간으로 나뉜다.
>    * **Stack (스택 영역 — 개인용 작은 메모장)** : 스레드(일꾼)마다 각자 1개씩 따로 지급되는 **약 1MB 크기의 좁은 메모장** 이다. 지금 실행 중인 함수의 지역 변수(`int x = 10`)와 함수가 끝나면 돌아갈 복귀 주소를 잠깐 적었다가 함수가 끝나면 즉시 지운다.
>    * **Heap (힙 영역 — 공용 대형 창고)** : 모든 스레드가 함께 쓰는 **수 기가바이트(GB) 크기의 거대한 창고** 이다. `new` 키워드로 만든 모든 객체(`new User()`, `new ArrayList<>()`)는 전부 이 힙 창고에 보관되며, 가비지 컬렉터(GC)가 주기적으로 돌아다니며 안 쓰는 쓰레기 객체를 치운다.
> 2. **OOM (`OutOfMemoryError`) 서버 다운이란?** :
>    * 위에서 말한 공용 대형 창고인 **JVM Heap 메모리가 100% 꽉 차서, 더 이상 새로운 객체를 단 1개도 만들 수 없을 때 자바 가상 머신(JVM)이 내뿜는 치명적 사망 선고** 이다. OOM이 터지면 해당 요청만 실패하는 것이 아니라, **웹 서버 프로세스 전체가 아예 멈추거나 강제 종료** 되어 서비스가 전면 중단된다.
> 3. **모니터 락 (Monitor Lock / `synchronized`)이란?** :
>    * 쉽게 말해 **'1인용 화장실 문고리(자물쇠)'** 이다. 여러 스레드(일꾼)가 동시에 하나의 객체 데이터를 건드리면 값이 꼬이므로, 자바는 모든 객체마다 '모니터(Monitor)'라는 보이지 않는 자물쇠를 달아두었다.
>    * 메서드에 `synchronized` 키워드를 붙이면, 스레드가 그 함수를 실행하기 전에 **무조건 화장실 열쇠(모니터 락)를 획득하고 문을 잠근 뒤에야** 들어갈 수 있다. 문제는 화장실을 **나 혼자(단일 스레드)** 쓸 때도 매번 열쇠를 찾고, 문을 잠그고, 나올 때 문을 여는 확인 절차를 거쳐야 해서 속도가 느려진다는 점이다.
> 4. **스레드 풀 (Thread Pool)과 `Executors.newFixedThreadPool(10)`이란?** :
>    * **스레드 풀** 은 쉽게 말해 **'콜센터의 고정 상담원 대기실과 번호표 대기열(Queue)'** 이다. 손님(요청)이 올 때마다 상담원(스레드)을 새로 채용하고 해고하면 비용이 너무 많이 들기 때문에, 미리 상담원 N명을 채용해 두고 대기열(Queue)에서 순서대로 일을 꺼내 처리하게 만든 구조이다.
>    * **`Executors.newFixedThreadPool(10)`** 은 자바가 기본 제공하는 편리한 스레드 풀 생성기로, **"고정 상담원 10명을 뽑아라. 그리고 10명이 모두 통화 중일 때 추가로 걸려오는 전화는 대기열(Queue)에 줄을 세워라"** 라는 코드이다. 치명적인 함정은 이 기본 대기열의 최대 크기가 **21억 명(`Integer.MAX_VALUE`, 사실상 무제한)** 으로 설정되어 있다는 점이다.
> 5. **`ArrayBlockingQueue`란?** :
>    * 크기가 고정된 배열로 만든 **'멀티스레드 전용 안전 대기열'** 이다. 생성할 때 `new ArrayBlockingQueue<>(1000)`처럼 **최대 줄 설 수 있는 인원(예: 1,000명)을 엄격하게 제한** 한다.
>    * 여러 스레드가 동시에 넣고 빼도 데이터가 깨지지 않도록 내부적으로 자물쇠(`ReentrantLock`)가 채워져 있으며, 큐가 꽉 차면 새 작업을 막고(**Blocking**) 큐가 비어 있으면 상담원 스레드를 대기시키는 똑똑한 통제 장치이다.

### 사례 1. AI 코드 함정: 레거시 `java.util.Stack` 사용으로 인한 불필요한 모니터 락(Lock) 부하와 LIFO 불변식 파괴
AI에게 "자바에서 괄호 유효성 검사나 DFS(깊이 우선 탐색)를 스택으로 구현해 줘"라고 요청하면, 인터넷의 오래된 코드들을 학습한 영향으로 `Stack<String> stack = new Stack<>();`을 생성하는 경우가 매우 흔하다.

```java
// [AI가 습관적으로 작성하는 레거시 Stack 코드]
Stack<String> history = new Stack<>();
history.push("Page1"); // 내부적으로 모니터 락(synchronized) 획득 및 해제 발생!
history.push("Page2"); // 또 모니터 락 획득 및 해제 발생!

// 치명적 설계 결함: Stack은 Vector를 상속받았기 때문에 중간 인덱스 삽입/조회가 열려 있음!
history.add(0, "HackedPage"); // LIFO(후입선출) 원칙이 완전히 깨짐!
String bottom = history.get(0); // 스택인데 맨 바닥의 요소를 마음대로 꺼내 봄!
```

#### ① 왜 이런 현상이 발생했는가? (원인 해부)
1. **불필요한 모니터 락(`synchronized`) 오버헤드** :
   * `java.util.Stack`의 내부 소스 코드를 열어보면 `public class Stack<E> extends Vector<E>`로 선언되어 있고, `push()`, `pop()`, `peek()` 메서드가 전부 `synchronized` 키워드로 감싸져 있다.
   * 함수 안에서 나 혼자 쓰는 지역 변수 스택인데도, 데이터를 100만 번 넣고 뺄 때마다 **200만 번이나 '1인용 화장실 자물쇠(모니터 락)'를 잠갔다 푸는 무의미한 작업** 을 반복하느라 CPU 클럭을 낭비한다.
2. **객체지향 캡슐화(LIFO 규칙) 파괴** :
   * 스택은 오직 맨 위(`Top`)에서만 데이터를 넣고 뺄 수 있어야 스택이다. 하지만 `Vector`(동적 배열)를 무분별하게 상속받았기 때문에, `add(index, item)`나 `remove(index)`로 스택의 허리를 임의로 잘라 넣거나 뺄 수 있어 자료구조의 신뢰성이 무너진다.

#### ② 실무적 해결책
* 단일 스레드에서 스택이 필요할 때는 락 오버헤드가 전혀 없고 양 끝 출입만 깔끔하게 허용하는 **`ArrayDeque`** 을 `Deque` 인터페이스로 선언해 사용한다.

```java
// Java 공식 문서(Javadoc)가 권장하는 현대적 표준 스택 선언 방식
Deque<String> history = new ArrayDeque<>();
history.push("Page1");      // 내부적으로 addFirst() 호출 (모니터 락 비용 0!)
history.push("Page2");
String top = history.pop(); // 내부적으로 removeFirst() 호출 (원형 배열 포인터만 이동 -> 초고속 O(1))
```

* **면접 포인트** : "`java.util.Stack`은 메서드마다 모니터 락(`synchronized`)이 걸려 있어 단일 스레드 성능이 떨어지고, `Vector`를 상속받아 LIFO 캡슐화가 깨져 있으므로 `ArrayDeque`을 사용해야 합니다"라고 답하면 완벽하다.

### 사례 2. 현업 개발자 설계 실수: `Executors.newFixedThreadPool(10)`의 무제한 큐(Unbounded Queue)로 인한 OOM 서버 사망
쇼핑몰에서 주문이 완료될 때마다 외부 알림 서버에 카카오톡 알림톡을 비동기로 발송하기 위해, 개발자가 `Executors.newFixedThreadPool(10)`으로 스레드 풀을 만들었다가 이벤트 트래픽이 몰리는 날 **웹 서버 전체가 `OutOfMemoryError(OOM)`로 다운된 실제 장애 사례** 이다.

```java
// [현업에서 매우 흔하게 저지르는 치명적 설계 실수]
// 스레드(일꾼)는 10개지만, 내부 대기열은 new LinkedBlockingQueue<>()로 최대 용량이 21억 개(무제한)!
ExecutorService executor = Executors.newFixedThreadPool(10);

@PostMapping("/orders")
public ResponseEntity<Void> createOrder(@RequestBody OrderDto dto) {
    // 주문은 초당 5,000건씩 들어오는데, 외부 알림 서버가 느려져서 일꾼 10명은 초당 50건밖에 처리 못 함!
    executor.submit(() -> externalKakaoApi.send(dto)); // 남은 초당 4,950건이 대기열(Queue)에 무한정 쌓임!
    return ResponseEntity.ok().build();
}
```

#### ① 왜 이런 현상이 발생했는가? (메모리 밑바닥 추적)
`Executors.newFixedThreadPool(10)`의 내부 구현 코드를 까보면 다음과 같이 작성되어 있다.

```java
// JDK 내부 Executors 클래스의 실제 코드
public static ExecutorService newFixedThreadPool(int nThreads) {
    return new ThreadPoolExecutor(nThreads, nThreads, 0L, TimeUnit.MILLISECONDS,
        new LinkedBlockingQueue<Runnable>()); // <-- 기본 생성자: 용량이 Integer.MAX_VALUE (2,147,483,647개)!
}
```

```text
[트래픽 폭주 및 외부 API 지연 시 JVM Heap 메모리에서 벌어지는 참사]

유입 속도: 초당 5,000건 ──> [ 무제한 대기열 (LinkedBlockingQueue: 한도 21억 개) ] ──> [일꾼 스레드 10개]
                           [주문1][주문2][주문3] ... [주문300,000] (계속 쌓임!)       (외부 지연으로 초당 50건만 처리)
                           └─────────── JVM Heap 메모리 4GB 100% 고갈! ──────────┘
                                                     │
                                                     ▼
                                    java.lang.OutOfMemoryError 발생!
                                    (결제, 로그인 등 서버의 모든 기능 동반 사망!)
```

* 평소에는 일꾼 10명이 빠르게 알림을 보내 대기열이 비어 있었다.
* 그러나 외부 알림 서버가 느려져 일꾼 10명의 처리 속도가 **초당 50건** 으로 떨어지자, 매초 처리되지 못한 **4,950건의 `OrderDto` 객체와 `LinkedList` 노드 객체가 무제한 큐에 그대로 쌓이기 시작** 했다.
* 큐의 한도가 21억 개다 보니 큐는 아무런 경고도 없이 힙 메모리가 다 찰 때까지 작업을 받아들였고, 불과 1~2분 만에 수십만 개의 대기 작업이 공용 창고인 **JVM Heap 메모리를 가득 채워 서버 전체가 OOM으로 사망** 했다.

#### ② 실무적 해결책 (`ArrayBlockingQueue`로 큐 크기 제한 + 거절 정책 설계)
* 실무에서는 절대 `Executors.newFixedThreadPool()`을 그대로 쓰지 않고, **`ThreadPoolExecutor`를 직접 생성하면서 `ArrayBlockingQueue`를 넣어 대기열의 최대 크기를 물리적으로 제한(Bounded Queue)** 해야 한다.

```java
// 1. ArrayBlockingQueue를 사용해 대기열의 최대 수용 인원을 1,000개로 엄격히 제한!
// -> 아무리 트래픽이 폭주해도 큐에는 딱 1,000개만 올라가므로 JVM Heap 메모리(OOM)가 절대 터지지 않음!
BlockingQueue<Runnable> boundedQueue = new ArrayBlockingQueue<>(1000);

// 2. 대기열 1,000칸이 꽉 찼을 때 1,001번째 작업이 들어오면 어떻게 대응할지 방어 정책(Rejection Policy) 명시
ExecutorService safeExecutor = new ThreadPoolExecutor(
    10,                                      // 기본 일꾼 스레드 10개
    20,                                      // 대기열이 꽉 차면 일꾼을 최대 20개까지 임시 증원
    60L, TimeUnit.SECONDS,
    boundedQueue,                            // 1,000칸 제한 안전 큐 장착
    new ThreadPoolExecutor.CallerRunsPolicy() // 또는 AbortPolicy / DiscardPolicy 선택
);
```

* **면접 포인트** : 비동기 큐를 설계할 때는 반드시 **"큐의 상한선(Bounded Queue) 설정"** 과 **"큐가 가득 찼을 때의 방어 전략(예: 예외를 던져 빠른 실패를 유도하는 `AbortPolicy`, 요청 스레드가 직접 처리해 유입 속도를 늦추는 `CallerRunsPolicy` 등)"** 을 세트로 답변해야 시니어급 설계 역량을 인정받는다.

### 사례 3. 현업 개발자 구현 실수: 깊이 제한 없는 재귀 호출로 인한 JVM Stack 폭발 (`StackOverflowError`)
쇼핑몰의 다단계 카테고리 트리(대분류 → 중분류 → 소분류...)에서 최상위 루트 카테고리를 찾는 함수를 재귀(Recursion)로 구현했다가, DB 데이터 입력 실수로 순환 참조가 발생하거나 깊이가 깊어졌을 때 스레드가 즉사하는 사례이다.

```java
// [실수 패턴: 콜 스택(Call Stack)의 물리적 한계를 무시한 재귀 함수]
public Category findRootCategory(Category current) {
    if (current.getParent() == null) {
        return current;
    }
    // 만약 DB 데이터 오류로 A의 부모가 B이고, B의 부모가 다시 A로 묶여 있다면? (무한 재귀 호출!)
    return findRootCategory(current.getParent()); 
}
```

#### ① 왜 이런 현상이 발생했는가? (JVM Stack 영역 해부)
* 앞서 빌드업에서 살펴보았듯, 각 스레드에게 할당된 개인 메모장인 **JVM Stack 영역의 기본 크기는 고작 1MB(`-Xss1m`)** 에 불과하다.
* `findRootCategory()`가 자기 자신을 다시 호출할 때마다, 아직 기존 함수가 끝난 것이 아니므로 스택 메모장 위에 새로운 **스택 프레임(매개변수 `current`, 복귀 주소 등 약 수십 바이트)** 이 프링글스 감자칩처럼 계속 쌓인다.
* 호출 깊이가 약 10,000~20,000번을 넘어가는 순간 1MB 메모장이 천장을 뚫고 넘치면서 **`java.lang.StackOverflowError`** 가 발생한다.

#### ② 실무적 해결책
* 깊이를 예측할 수 없는 계층 탐색이나 그래프 탐색(DFS)은 1MB짜리 좁은 콜 스택(재귀)에 의존하지 않고, **수 기가바이트(GB)의 넉넉한 공용 창고(JVM Heap)에 생성되는 `ArrayDeque`과 `while` 반복문** 으로 풀어서 작성한다.

```java
// 재귀(Call Stack) 대신 반복문(Loop)과 안전장치(방문 체크)를 사용하여 StackOverflow 원천 차단!
public Category findRootCategorySafe(Category current) {
    Set<Long> visitedIds = new HashSet<>(); // 순환 참조(무한 루프) 방지용
    Category pointer = current;
    
    while (pointer.getParent() != null) {
        if (!visitedIds.add(pointer.getId())) {
            throw new IllegalStateException("카테고리 순환 참조 데이터 오류가 감지되었습니다.");
        }
        pointer = pointer.getParent(); // 스택 프레임을 쌓지 않고 변수 참조만 교체 (공간 복잡도 O(1))
    }
    return pointer;
}
```

## 3. Deep Dive: 밑바닥 동작 원리와 연쇄 의문 해부

### 3-1. CPU와 JVM의 심장: 콜 스택(Call Stack)의 하드웨어 동작 원리
프로그램이 실행될 때 왜 함수 호출 관리에 큐(Queue)가 아닌 **스택(Stack, LIFO)** 을 쓸 수밖에 없는지 메모리 구조로 추적한다.

```text
[코드 실행 흐름]
void main() { int x = 10; order(x); }
void order(int a) { int y = 20; pay(y); }
void pay(int b) { /* 결제 완료 후 return */ }

[RAM의 Call Stack 메모리 영역 변화]

  (1) main() 실행 중         (2) order() 호출 시         (3) pay() 호출 시
+--------------------+     +--------------------+     +--------------------+
| [Frame 1: main()]  |     | [Frame 1: main()]  |     | [Frame 1: main()]  |
| - 지역변수 x = 10   |     | - 지역변수 x = 10   |     | - 지역변수 x = 10   |
+--------------------+     +--------------------+     +--------------------+
  ▲ RSP (Stack Pointer)    | [Frame 2: order()] |     | [Frame 2: order()] |
                           | - 복귀주소: main()  |     | - 복귀주소: main()  |
                           | - 매개변수 a = 10   |     | - 매개변수 a = 10   |
                           | - 지역변수 y = 20   |     | - 지역변수 y = 20   |
                           +--------------------+     +--------------------+
                             ▲ RSP                    | [Frame 3: pay()]   |
                                                      | - 복귀주소: order() |
                                                      | - 매개변수 b = 20   |
                                                      +--------------------+
                                                        ▲ RSP (현재 실행 위치)
```

1. **왜 무조건 LIFO(스택)여야만 하는가?** :
   * `main()`이 끝나려면 그 안에서 부른 `order()`가 먼저 끝나야 하고, `order()`가 끝나려면 그 안에서 부른 `pay()`가 가장 먼저 끝나야 한다. 즉, **"가장 나중에 호출된 함수가 가장 먼저 종료되고 빠져나와야(Last-In, First-Out)"** 프로그램의 인과관계가 성립한다.
2. **스택 팝(Pop)을 통한 메모리 해제가 0클럭 수준인 이유** :
   * `pay()` 함수가 끝날 때 CPU는 메모리에 적힌 `b = 20`이라는 비트들을 일일이 `0`으로 지우지 않는다.
   * 단지 CPU 내부의 **스택 포인터 레지스터(`RSP`, 현재 스택의 꼭대기 위치를 가리키는 화살표) 주소값만 `Frame 2`의 끝 위치로 한 칸 되돌릴 뿐** 이다. 이후 다른 함수가 호출되면 옛날 `Frame 3` 데이터 위에 새 데이터를 그대로 덮어쓰므로, 스택의 메모리 할당과 해제는 산술 연산 단 1클럭으로 끝난다.

### 3-2. 원형 배열(Circular Array) 기반의 `ArrayDeque` 동작 원리
일반 배열(`ArrayList`)로 큐를 만들면 맨 앞(`0`번 인덱스) 데이터를 뺄 때마다 뒤에 남은 모든 데이터를 한 칸씩 앞으로 당겨와야 해서 **O(N)** 이 걸린다. `ArrayDeque`은 데이터를 한 칸도 움직이지 않고 **`head`(앞문)와 `tail`(뒷문) 두 개의 인덱스 화살표만 빙글빙글 돌리는 원형 배열(Circular Buffer)** 로 이 문제를 해결한다.

```text
[ArrayDeque 원형 배열의 포인터 회전 과정 (배열 크기 = 8)]

1. 초기 삽입: offerLast(A), offerLast(B), offerLast(C)
인덱스 :   [0]     [1]     [2]     [3]     [4]     [5]     [6]     [7]
데이터 :  [ A ]   [ B ]   [ C ]   [   ]   [   ]   [   ]   [   ]   [   ]
           ▲                       ▲
          head                    tail (다음에 들어올 빈칸 위치)

2. 맨 앞 추출: pollFirst() -> 'A' 반환 (뒤쪽 B, C를 당기지 않고 head 화살표만 0 -> 1로 이동! -> 진짜 O(1))
인덱스 :   [0]     [1]     [2]     [3]     [4]     [5]     [6]     [7]
데이터 :  [null]  [ B ]   [ C ]   [   ]   [   ]   [   ]   [   ]   [   ]
                   ▲               ▲
                  head            tail

3. 배열 끝 도달 후 0번으로 회전 (Wrap-Around): tail이 7번을 채운 뒤 다음 데이터(H)가 들어오면 비어 있는 0번 칸으로 회전!
인덱스 :   [0]     [1]     [2]     [3]     [4]     [5]     [6]     [7]
데이터 :  [ H ]   [ B ]   [ C ]   [ D ]   [ E ]   [ F ]   [ G ]   [ I ]
                   ▲       ▲
                  tail    head (tail이 한 바퀴 돌아 head와 만나는 순간 배열이 꽉 찬 것으로 판단 -> 2배 확장!)
```

### 3-3. 꼬리에 꼬리를 무는 의문 해결

#### 의문 1. "`ArrayDeque`은 왜 내부 배열의 크기를 10이나 15가 아니라 무조건 2의 거듭제곱(8, 16, 32, 64...)으로만 유지하는가?"
원형 배열에서 화살표(`head`, `tail`)가 배열의 끝까지 갔을 때 다시 `0`번 인덱스로 돌아오거나, `0`번에서 뒤로 한 칸 갈 때 배열의 맨 끝 인덱스로 넘어가려면 **순환 인덱스 계산** 이 필요하다. 이때 **CPU에서 매우 느린 나눗셈 나머지 연산(`%`)을 없애고, 단 1클럭 만에 끝나는 초고속 비트 연산(`&`, Bitwise AND)을 쓰기 위해서** 이다.

##### ① 일반 크기의 배열일 때: 느린 나머지 연산(`%`)과 음수 처리의 고통
배열 크기가 `10`이라고 가정하자.
* 앞으로 갈 때(`tail + 1`): `9`번 칸 다음은 `(9 + 1) % 10 = 0`번 칸이 된다.
* 문제는 **CPU의 산술논리연산장치(ALU)에서 나눗셈(`/`, `%`)은 덧셈이나 비트 연산보다 약 20~30배 느린(약 20~40클럭 소모) 매우 무거운 연산** 이라는 점이다.
* 게다가 `addFirst()`를 호출해 `head`가 `0`번 칸에서 왼쪽으로 한 칸(`0 - 1 = -1`) 이동할 때는, 자바에서 `(-1) % 10 = -1`이 나와버려 `ArrayIndexOutOfBoundsException`이 터진다. 이를 막으려면 `if (head < 0) head += length;` 같은 분기문까지 매번 실행해야 한다.

##### ② 배열 크기가 2의 거듭제곱(`2^k`)일 때 일어나는 2진수의 마법
배열의 크기(`length`)를 **2의 거듭제곱(예: 8, 16, 32)** 으로 맞추면, **`length - 1`의 2진수 비트가 하위 자리만 전부 `1`로 꽉 찬 형태(비트 마스크)** 가 된다.

```text
[배열 크기(length)가 8 (2^3)일 때의 2진수 비트 구조]
length     = 8  ──(2진수)──>  0000 1000
length - 1 = 7  ──(2진수)──>  0000 0111  <-- 하위 3비트가 모두 1인 완벽한 필터(Mask)가 됨!
```

이 상태에서 어떤 숫자든 `(length - 1)`과 **비트 AND 연산(`&`, 둘 다 1일 때만 1)** 을 수행하면, `8` 이상으로 넘어가는 앞자리 비트는 전부 `0`으로 잘려 나가고 **정확히 `8`로 나눈 나머지(`0 ~ 7`)만 남는다!**

```text
[Case 1: tail이 7번 끝칸에서 다음 칸(7 + 1 = 8)으로 넘어갈 때]
  (tail + 1)     = 8   ──>   0000 1000
& (length - 1)   = 7   ──> & 0000 0111
---------------------------------------
  결과 인덱스      = 0   ──>   0000 0000  (나눗셈 없이 단 1클럭 만에 0번 인덱스로 순환!)

[Case 2: head가 0번 첫칸에서 뒤로 한 칸(0 - 1 = -1) 물러날 때 (addFirst)]
  (head - 1)     = -1  ──>   1111 1111  (2의 보수 표현법에 의해 모든 비트가 1)
& (length - 1)   = 7   ──> & 0000 0111
---------------------------------------
  결과 인덱스      = 7   ──>   0000 0111  (if 분기문 없이 단 1클럭 만에 맨 끝 7번 인덱스로 순환!)
```

```java
// 실제 Java ArrayDeque 내부 소스 코드
// 1. 맨 뒤에 추가할 때 (tail을 오른쪽으로 한 칸 회전)
elements[tail] = e;
tail = (tail + 1) & (elements.length - 1); // (tail + 1) % length 와 동일하지만 속도는 수십 배 빠름!

// 2. 맨 앞에 추가할 때 (head를 왼쪽으로 한 칸 회전)
head = (head - 1) & (elements.length - 1); // head가 0일 때도 if문 없이 즉시 맨 끝 인덱스로 점프!
elements[head] = e;
```

* 만약 배열 크기가 `10`이라면 `length - 1`은 `9` (`0000 1001`)가 되어 중간 비트가 `0`으로 뚫려 있으므로 이 비트 연산 공식이 절대 성립하지 않는다.
* 즉, **`ArrayDeque`(그리고 다음 단원에서 배울 `HashMap`)이 내부 배열 크기를 무조건 2의 거듭제곱으로 강제하는 이유는, 느린 나눗셈(`%`)과 음수 분기(`if`)를 단 1클럭짜리 비트 AND 연산(`& (length - 1)`) 하나로 대체하기 위한 극한의 하드웨어 최적화** 이다.

---

#### 의문 2. "원형 배열인 `ArrayDeque`에 데이터가 계속 들어와 `head`와 `tail`이 똑같은 칸에서 만나버리면 어떻게 크기를 확장(Doubling)하는가?"
`tail`이 한 바퀴를 돌아 `head`와 같아지는 순간(`tail == head`), 빈칸이 하나도 남지 않은 만원 상태이다. 이때 `ArrayDeque`은 기존 용량의 **정확히 2배(`capacity << 1`, 여전히 2의 거듭제곱 유지)** 크기의 새 배열을 만들고, 원형으로 꼬여 있던 순서를 반듯하게 펴서 복사한다.

```text
[만차 상태의 원형 배열 (Capacity = 8, head = 2, tail = 2)]
인덱스 :  [0]   [1]   [2]   [3]   [4]   [5]   [6]   [7]
데이터 : [ G ] [ H ] [ A ] [ B ] [ C ] [ D ] [ E ] [ F ]
                      ▲
                  head == tail (A가 맨 앞 데이터, H가 맨 뒤 데이터)

[2배 확장(Capacity = 16) 및 일직선 정렬 복사 (System.arraycopy 2회 수행)]
1차 복사: head(2번)부터 배열 끝(7번)까지의 [A, B, C, D, E, F]를 새 배열의 0번부터 복사
2차 복사: 0번부터 head 앞(1번)까지의 [G, H]를 그 뒤에 이어서 복사

확장 완료된 새 배열 (Capacity = 16):
인덱스 :  [0]   [1]   [2]   [3]   [4]   [5]   [6]   [7]   [8]  ... [15]
데이터 : [ A ] [ B ] [ C ] [ D ] [ E ] [ F ] [ G ] [ H ] [   ] ... [   ]
          ▲                                               ▲
         head = 0                                        tail = 8
```

#### 의문 3. "`ArrayDeque`이 그렇게 완벽하다면 왜 이름에 `null`을 넣지 못하게 막아두었는가?"
`ArrayList`나 `LinkedList`는 `list.add(null)`이 가능하지만, `ArrayDeque`에 `deque.offer(null)`을 호출하면 즉시 `NullPointerException`을 던지며 거부한다.
* **이유** : 큐에서 데이터를 꺼내는 `poll()` 메서드는 **"큐가 비어 있을 때 `null`을 반환"** 하도록 설계되어 있다. 만약 큐 안에 실제 데이터로 `null`을 넣는 것을 허용해 버리면, `poll()`의 결과가 `null`로 나왔을 때 **"큐가 진짜로 비어 있어서 `null`이 나온 건지, 아니면 누군가 넣어둔 `null` 데이터가 꺼내진 건지"** 구분할 방법이 없기 때문이다. 또한 내부 배열에서 삭제된 빈 슬롯을 `null`로 표시해 GC가 수거하게 만드는데, 실제 원소 `null`과 빈칸 `null`이 섞이는 모호함을 원천 차단하기 위해 `null` 삽입을 금지했다.

## 4. 핵심 요약 및 기술 면접 대비 (한국 IT 기업 기준)

### ① 개발 과정을 이해하기 위해 챙겨야 할 감각
* **코드 한 줄이 만드는 메모리 파동** : 내가 함수를 호출할 때는 **JVM Stack 영역(1MB)** 에 프레임이 쌓이고, `new`로 객체를 만들거나 큐에 작업을 넣을 때는 **JVM Heap 영역(수 GB)** 이 소모된다는 물리적 지도를 머릿속에 그려야 한다.
* **단일 스레드 vs 멀티스레드 큐의 명확한 구분** :
  * 함수 내부에서 나 혼자 알고리즘(DFS/BFS)이나 임시 버퍼로 쓸 때는 락(Lock)이 없는 초고속 **`ArrayDeque`** 을 쓴다.
  * 여러 스레드가 동시에 작업을 넣고 빼는 서버 스레드 풀이나 비동기 파이프라인에서는 반드시 스레드 안전(Thread-Safe)하고 최대 크기가 제한된 **`ArrayBlockingQueue`** 를 쓴다.

### ② 면접 모범 답변 스크립트
> **Q. "Java에서 스택이나 큐를 구현할 때 어떤 컬렉션을 사용하시나요? `Stack`이나 `LinkedList`와 비교해서 설명해 주세요."**
>
> "단일 스레드 환경에서 스택이나 큐가 필요할 때는 항상 **`ArrayDeque`** 을 사용합니다.
> 첫째로 레거시 클래스인 `java.util.Stack`은 `Vector`를 상속받아 모든 메서드에 `synchronized` 모니터 락이 걸려 있어 단일 스레드에서 불필요한 성능 저하가 발생하고, 인덱스 기반 중간 접근이 열려 있어 LIFO 원칙이 깨지기 때문입니다.
> 둘째로 `LinkedList`를 큐로 사용하면 데이터를 넣고 뺄 때마다 24바이트 크기의 `Node` 객체를 매번 힙에 새로 생성하고 버려야 해서 Young 영역의 GC 부하가 커지고 포인터 추적 때문에 CPU 캐시 효율이 떨어집니다.
> 반면 `ArrayDeque`은 내부적으로 크기가 2의 거듭제곱인 **원형 배열(Circular Array)** 을 사용하여 비트 AND 연산으로 `head`와 `tail` 인덱스만 이동시키므로, **양 끝 삽입·삭제가 모두 O(1)이면서 추가 객체 생성이 없고 캐시 지역성까지 극대화** 할 수 있습니다."
