# M2-3. 흩어진 메모리의 연결 — 연결 리스트(Singly / Doubly Linked List)

## 1. 면접 핵심 Q&A

### Q1. 배열(ArrayList)과 연결 리스트(LinkedList)의 물리적 메모리 구조와 성능 차이는 무엇인가요?
**배열(ArrayList)** 은 데이터가 메모리(RAM)의 연속된 공간에 빈틈없이 나열되는 구조이고, **연결 리스트(LinkedList)** 는 데이터가 힙(Heap) 메모리 곳곳에 흩어져 생성되되 각 노드가 이전·다음 노드의 메모리 주소값(포인터)을 들고 논리적으로 연결된 구조이다.

이 물리적 배치 차이로 인해 조회와 삽입·삭제에서 정반대의 트레이드오프를 가진다.

| 비교 항목 | 단일 연결 리스트 (Singly) | 이중 연결 리스트 (Java `LinkedList`) | 동적 배열 (`ArrayList`) | 원형 동적 배열 (`ArrayDeque`) |
| :--- | :--- | :--- | :--- | :--- |
| **메모리 배치** | 힙 곳곳에 비연속 노드 분산 | 힙 곳곳에 비연속 노드 분산 | 내부 참조 배열 연속 배치 | 내부 참조 배열 원형 배치 |
| **인덱스 조회 (`get`)** | **O(N)** (Head부터 순차 탐색) | **O(N)** (Head/Tail 가까운 쪽 탐색) | **O(1)** (산술 연산 직접 접근) | 인덱스 직접 조회 미지원 |
| **양 끝 삽입 / 삭제** | Head: **O(1)** / Tail: **O(N)** (Tail 포인터 없을 시) | **양 끝 모두 O(1)** (`First`, `Last`) | 끝 추가: 분할 상환 **O(1)** / 앞 삽입·삭제: **O(N)** | **양 끝 모두 분할 상환 O(1)** |
| **위치 탐색 포함 중간 삽입/삭제** | **O(N)** (탐색 **O(N)** + 연결 **O(1)**) | **O(N)** (탐색 **O(N)** + 연결 **O(1)**) | **O(N)** (탐색 **O(1)** + 쉬프트 **O(N)**) | 중간 삽입/삭제 미지원 |
| **이미 노드(Iterator)를 알 때 삽입/삭제** | 이전 노드를 몰라 삭제 시 **O(N)** | **O(1)** (`ListIterator` 활용) | **O(N)** (뒤쪽 원소 이동 필수) | 해당 없음 |
| **요소당 관리 메모리 오버헤드** | 약 **16~20 Byte** (`item` + `next`) | 약 **24 Byte** (`item` + `prev` + `next`) | **4 Byte** (참조 슬롯 1칸) | **4 Byte** (참조 슬롯 1칸) |
| **CPU 캐시 효율** | 낮음 (포인터 체이싱 발생) | 낮음 (포인터 체이싱 + 24B 비대화) | **매우 높음** (공간 지역성 극대화) | **매우 높음** (공간 지역성 극대화) |

### Q2. Java의 `LinkedList` 는 왜 단일 연결 리스트가 아닌 이중 연결 리스트(Doubly Linked List)로 구현되어 있나요?
노드당 `prev` 포인터(4바이트)를 추가로 소모함에도 불구하고 **양방향 탐색과 O(1) 역방향 삭제** 를 지원하기 위해서이다.
1. **양 끝단 연산의 완벽한 O(1) 보장**: 단일 연결 리스트는 맨 뒤(`Tail`) 노드를 삭제할 때, 직전 노드를 찾기 위해 처음(`Head`)부터 끝까지 **O(N)** 으로 다시 걸어가야 한다. 반면 이중 연결 리스트는 `Tail.prev` 를 통해 직전 노드에 즉시 접근하므로 맨 앞과 맨 뒤의 삽입·삭제를 모두 **O(1)** 에 처리한다.
2. **탐색 횟수 절반 단축**: 인덱스 조회 시 찾으려는 위치가 전체 크기의 절반(`size / 2`)보다 앞쪽이면 `Head` 에서 출발하고, 뒤쪽이면 `Tail` 에서 `prev` 를 타고 거꾸로 출발하여 탐색 범위를 최대 절반(**N/2**)으로 줄인다.
3. **`Iterator` 삭제 효율**: 순회 도중 현재 노드를 삭제(`iterator.remove()`)할 때, 이전 노드가 누구인지 별도로 추적하지 않아도 현재 노드의 `prev` 와 `next` 만 서로 이어주면 즉시 **O(1)** 삭제가 완료된다.

### Q3. 실무에서 큐(Queue)나 스택(Stack)을 구현할 때 왜 `LinkedList` 대신 `ArrayDeque` 을 권장하나요?
**GC(가비지 컬렉션) 부하 감소** 와 **CPU 캐시 지역성(Spatial Locality)** 두 가지 측면에서 `ArrayDeque` 이 압도적으로 유리하기 때문이다.
* `LinkedList` 는 데이터를 넣고 뺄 때마다 24바이트짜리 `Node` 포장지 객체를 힙 메모리에 매번 새로 생성(`new Node()`)하고 버리므로 불필요한 메모리 할당과 GC 오버헤드를 유발한다. 또한 노드가 메모리에 흩어져 있어 CPU 캐시 미스가 잦다.
* 반면 `ArrayDeque` 은 연속된 내부 배열을 원형(Circular)으로 재사용하며 `head` 와 `tail` 인덱스 숫자만 이동시킨다. 새 노드 객체를 전혀 생성하지 않아 GC 부하가 없고, 연속된 메모리를 사용하므로 캐시 효율이 극대화된다.

## 2. 실무 사례

### 사례 1. `List` 추상화 뒤에 숨은 `get(i)` 순회와 `remove(index)` 의 O(N²) 서버 마비 (현업 개발자의 흔한 실수)
자바 백엔드에서는 유연성을 위해 파라미터를 `List<T>` 인터페이스로 받는다. 이때 누군가 `LinkedList` 를 넘겨주었는데, 이를 처리하는 개발자가 습관적으로 인덱스 기반 `for` 문을 돌려 API가 타임아웃으로 멈춰버린 사례이다.

```java
// [문제가 된 실수 코드 1: LinkedList를 get(i)로 순회]
public void sendNotifications(List<User> targetUsers) { 
    // 호출부에서 10만 건이 담긴 LinkedList를 넘겨준 상황!
    for (int i = 0; i < targetUsers.size(); i++) {
        // 매 반복마다 0번(Head)부터 i번째까지 처음부터 다시 걸어감! -> 1회당 O(N)
        User user = targetUsers.get(i); 
        pushService.send(user);
    }
}

// [문제가 된 실수 코드 2: "삭제가 빠르다니까 LinkedList를 쓰자!"며 인덱스로 반복 삭제]
for (int i = 0; i < linkedList.size(); i++) {
    if (linkedList.get(i).isInactive()) {
        linkedList.remove(i); // i번째까지 찾아가는 데 O(N) 소요!
    }
}
```

#### ① 원인 분석: 왜 O(N)이 아니라 O(N²) 재앙이 되는가?
`LinkedList` 는 배열처럼 방 번호(인덱스)로 단번에 점프할 수 없고, 무조건 맨 앞(`Head`)부터 징검다리를 하나씩 밟아가야 한다.
* `get(0)` 호출: 0번 이동
* `get(1)` 호출: 0번 → 1번 (1번 이동)
* `get(2)` 호출: **방금 읽었던 1번 위치를 기억하지 못하고, 다시 0번부터** → 1번 → 2번 (2번 이동)
* `get(99999)` 호출: 다시 0번부터 99,999번까지 처음부터 걸어감!

결국 10만 건을 다 읽으려면 1 + 2 + 3 + ... + 100,000 ≈ **약 50억 번의 메모리 점프(O(N²))** 가 발생한다. `linkedList.remove(i)` 역시 마찬가지로 연결을 끊는 작업만 **O(1)** 일 뿐, 그 `i` 번째 노드까지 찾아가는 과정이 **O(N)** 이므로 루프 안에서 호출하면 똑같이 **O(N²)** 이 된다.

#### ② 실무적 해결책 (상세 원리 해부): 향상된 `for-each`, `Iterator.remove()`, `removeIf()`

##### 해결책 A. 단순 순회할 때는 반드시 '향상된 `for-each` 문'을 사용한다
```java
// 향상된 for-each 문: O(N)으로 10만 건을 단 한 번에 순회 완료!
for (User user : targetUsers) {
    pushService.send(user);
}
```
* **왜 향상된 `for-each` 문은 빠른가? (내부 동작 원리)**:
  자바 컴파일러는 향상된 `for-each` 문을 만나면 내부적으로 **`Iterator` (반복자)** 라는 책갈피 객체를 사용하는 코드로 자동 변환한다.
  ```text
  [일반 get(i) 루프: 매번 처음(Head)부터 다시 걸어감]
  i=1: [Head] ──> [노드1]
  i=2: [Head] ──> [노드1] ──> [노드2]
  i=3: [Head] ──> [노드1] ──> [노드2] ──> [노드3]  (중복 걸음 폭증! O(N²))

  [향상된 for-each 문 (Iterator): 방금 읽은 위치에 '책갈피(현재 노드 포인터)'를 꽂아둠!]
  [Head] ──(1보)──> [노드1] ──(1보)──> [노드2] ──(1보)──> [노드3]
                      ▲                  ▲                  ▲
                 책갈피 이동!        책갈피 이동!        책갈피 이동! (항상 딱 1칸씩만 전진! O(N))
  ```
  `Iterator` 는 내가 방금 어느 노드를 읽었는지 그 메모리 주소를 변수(`next`)에 기억하고 있다. 따라서 다음 루프로 넘어갈 때 처음(`Head`)으로 돌아가지 않고, **현재 서 있는 자리에서 바로 옆 칸(`node.next`)으로 딱 한 발짝만 이동(O(1))** 한다. 덕분에 10만 건을 순회할 때 정확히 10만 번만 이동하여 **O(N)** 에 끝난다.

##### 해결책 B. 순회 도중 요소를 삭제할 때는 `Iterator.remove()` 또는 `removeIf()` 를 사용한다
주의할 점은 향상된 `for-each` 문 안에서는 리스트의 `targetUsers.remove(user)` 를 직접 호출하면 안 된다는 것이다. 순회 도중 리스트의 구조가 바뀌면 자바는 데이터 정합성이 깨졌다고 판단해 즉시 `ConcurrentModificationException` 에러를 터뜨린다.

따라서 순회하면서 안전하고 빠르게(**O(1)**) 삭제하려면 아래 두 가지 방법을 써야 한다.

```java
// [방법 1] 명시적으로 Iterator(또는 ListIterator)를 꺼내서 삭제 (전통적 방식)
Iterator<User> iterator = targetUsers.iterator();
while (iterator.hasNext()) {
    User user = iterator.next(); // 책갈피를 다음 노드로 한 칸 이동 (O(1))
    if (user.isInactive()) {
        // 현재 책갈피가 밟고 서 있는 바로 그 노드의 앞뒤 연결 고리만 즉시 끊어냄! (진짜 O(1))
        iterator.remove(); 
    }
}

// [방법 2] Java 8+의 removeIf() 사용 (실무에서 가장 권장하는 깔끔한 방식)
// 내부적으로 위 [방법 1]의 Iterator.remove() 코드를 똑같이 실행해 줌!
targetUsers.removeIf(user -> user.isInactive());
```
* **왜 `iterator.remove()` 와 `removeIf()` 는 O(1)에 삭제가 가능한가?**:
  일반 `list.remove(i)` 는 "0번부터 `i` 번째까지 걸어가서 지워라"라는 뜻이라 걸어가는 시간(**O(N)**)이 든다.
  반면 `iterator.remove()` 는 **"이미 내가 걸어오면서 지금 발로 밟고 서 있는 현재 노드(`lastReturned`)를 그 자리에서 바로 빼버려라"** 라는 명령이다. 이미 노드를 손에 쥐고 있으므로 탐색 시간이 **0** 이며, 현재 노드의 앞 노드(`prev`)와 뒤 노드(`next`)의 손만 서로 맞잡게 해주면 끝난다.
  `targetUsers.removeIf(조건식)` 는 이 번거로운 `while (iterator.hasNext())` 코드를 자바가 대신 돌려주는 문법적 설탕(Syntactic Sugar)이므로, 가독성과 **O(1)** 삭제 성능을 동시에 챙길 수 있다.

* **면접 포인트**: *"LinkedList는 삭제가 O(1)이다"* 라는 말은 반만 맞다. 인덱스로 찾아가서 지우면 **O(N)** 이고, **`Iterator` 나 `removeIf()` 를 통해 순회하며 현재 노드를 즉시 지울 때만 진정한 O(1)의 이점을 누릴 수 있다** 고 답해야 완벽하다.

### 사례 2. 큐(Queue)와 최근 조회 목록 구현에 습관적으로 `LinkedList` 를 남용해 발생한 GC 멈춤 현상 (AI 코드의 단골 함정)
AI에게 "자바에서 작업을 순서대로 처리하는 큐(Queue)를 만들어 줘" 혹은 "최근 들어온 요청 로그 1,000개를 유지하는 버퍼를 짜줘"라고 요청하면, AI는 십중팔구 `Queue<T> queue = new LinkedList<>();` 코드를 만들어 준다.

```java
// [AI가 습관적으로 생성하는 문제의 코드]
Queue<RequestLog> recentLogs = new LinkedList<>();

// 초당 10,000번(10,000 TPS) 호출되는 API 로깅 메서드
public void recordLog(RequestLog log) {
    if (recentLogs.size() >= 1000) {
        recentLogs.poll(); // 1. 맨 앞 데이터를 꺼냄 -> 기존 Node 포장지 객체가 쓰레기(Garbage)로 버려짐!
    }
    recentLogs.offer(log); // 2. 맨 뒤에 데이터 추가 -> 매번 new Node<>()로 24바이트 객체를 새로 만듦!
}
```

#### ① 무엇이 문제인가? (초보자도 이해할 수 있는 메모리 밑바닥 해부)
언뜻 보면 `LinkedList` 는 맨 앞 삭제(`poll`)와 맨 뒤 추가(`offer`)가 모두 **O(1)** 이니 완벽해 보인다. 하지만 컴퓨터 메모리(JVM Heap) 내부를 들여다보면 심각한 **'일회용 포장지 쓰레기 대란'** 이 벌어지고 있다.

이를 **'회전초밥집의 접시 관리'** 에 비유해 보자.
* **데이터(`RequestLog`)** 는 초밥이고, **`LinkedList` 의 노드(`Node`)** 는 초밥을 담는 플라스틱 접시이다.
* `LinkedList` 는 초밥(`log`)을 그냥 보관하지 못한다. 반드시 `offer(log)` 를 호출할 때마다 **`new Node(prev, log, next)` 라는 24바이트짜리 일회용 접시 객체를 메모리(Heap의 Eden 영역)에 새로 찍어내어** 그 위에 초밥을 올린다.
* 반대로 `poll()` 로 초밥을 꺼내 먹으면, 방금 썼던 `Node` 접시를 재활용하지 않고 **메모리 바닥에 그대로 버린다(Unreachable 상태의 쓰레기 객체 발생)**.

```text
[초당 10,000건 요청 시 LinkedList 큐에서 벌어지는 메모리 참사]

1초 동안 일어나는 일:
offer() 10,000번 실행 ──> 힙 메모리에 new Node() 포장지 10,000개 신규 생성! (240KB)
poll()  10,000번 실행 ──> 다 쓴 헌 Node() 포장지 10,000개가 메모리 쓰레기로 방치됨!

1분이 지나면? ──> 무려 600,000개(60만 개)의 일회용 Node 쓰레기가 JVM 메모리를 가득 채움!
결과 ──> 청소부(Garbage Collector, GC)가 쓰레기를 치우려고 서버의 모든 작업을 일시 정지(Stop-The-World)시킴!
```
1. **GC(가비지 컬렉션) 폭탄**: 서버 메모리가 일회용 `Node` 쓰레기들로 금방 차버리기 때문에, JVM의 청소부(GC)가 쉴 새 없이 출동해야 한다. GC가 메모리를 청소하는 순간에는 서버가 멈칫거리는 지연(Latency Spike)이 발생하고 CPU 자원이 낭비된다.
2. **CPU 캐시 미스**: 그때그때 새로 만들어진 `Node` 객체들은 메모리 여기저기에 흩어져 있어서, CPU가 데이터를 읽을 때마다 캐시 미스(Cache Miss)가 발생해 처리 속도가 느려진다.

---

#### ② 실무적 해결책 (상세 설명): 상황에 맞는 완벽한 대체재 2가지

##### 해결책 A. 단순 큐(FIFO)나 스택(LIFO)이 목적일 때 → `ArrayDeque` 사용
일회용 접시를 매번 만들고 버리는 `LinkedList` 대신, **커다란 회전 레일(배열) 하나를 깔아두고 계속 돌려 쓰는 `ArrayDeque`** 으로 교체한다.

```java
// LinkedList 대신 ArrayDeque으로 구현체만 변경!
Queue<RequestLog> recentLogs = new ArrayDeque<>(1000);
```
* **`ArrayDeque` 은 어떻게 동작길래 완벽한가? (원형 배열의 마법)**:
  1. **노드 포장지 생성 0회 (GC 부하 제로)**: `ArrayDeque` 은 처음에 1,000칸짜리 연속된 배열(`Object[]`) 하나만 딱 만들어 둔다. 데이터를 넣고 뺄 때 `new Node()` 같은 포장지 객체를 절대 만들지 않고, 배열의 빈칸에 데이터 참조값만 쏙 넣었다 뺀다. 따라서 메모리에 버려지는 쓰레기가 전혀 없다.
  2. **데이터를 밀고 당기지 않는 원형(Circular) 구조**: 앞서 배운 일반 `ArrayList` 는 맨 앞(`0`번)을 빼면 뒤쪽 데이터를 전부 앞으로 당겨와야 해서 **O(N)** 이 걸렸다. 반면 `ArrayDeque` 은 데이터를 가만히 두고 **'꺼낼 위치(`head` 화살표)'와 '넣을 위치(`tail` 화살표)' 번호만 한 칸씩 옆으로 옮긴다**.
  ```text
  [ArrayDeque의 원형 배열 재사용 원리: 데이터 이동도 없고, 새 객체 생성도 없다!]

  배열 칸:  [ 0번 ]   [ 1번 ]   [ 2번 ]   [ 3번 ]  (끝에 도달하면 다시 0번으로 뱅글뱅글 돎!)
             (비움)    [로그B]   [로그C]   [로그D]
                        ▲                 ▲
                       head              tail
          (poll 호출 시 head만 0->1로 이동! O(1))   (offer 호출 시 tail 다음 칸에 넣고 이동! O(1))
  ```
  3. **극강의 캐시 효율**: 연속된 배열이므로 CPU 캐시 라인에 한 번에 올라와 `LinkedList` 보다 실행 속도가 수배 이상 빠르다.

##### 해결책 B. "이미 들어있는 데이터를 찾아서 맨 뒤로 순서를 바꾸는 작업(LRU 캐시, 최근 본 상품 목록)"이 목적일 때 → `LinkedHashMap` (또는 `LinkedHashSet`) 사용
만약 쇼핑몰의 **'최근 본 상품 목록'** 처럼 아래 두 가지가 동시에 필요하다면 어떻게 해야 할까?
1. 들어온 순서대로 줄을 세워야 하고, 1,000개가 넘으면 가장 오래된 맨 앞 상품을 지워야 한다.
2. **그런데 사용자가 이미 목록 중간에 있는 '아이폰'을 또 클릭했다면?** 기존 중간에 있던 '아이폰'을 지우고 맨 최신 자리로 옮겨야 한다.

이때 `LinkedList` 나 `ArrayDeque` 만 쓰면, 중간에 '아이폰'이 들어있는지 찾고 지우는 데 처음부터 끝까지 뒤져야 하므로 **O(N)** 이 걸린다. 이럴 때 실무에서 쓰는 비장의 무기가 바로 **`LinkedHashMap` (또는 `LinkedHashSet`)** 이다.

```text
[LinkedHashMap의 구조: 해시 테이블의 O(1) 검색 + 이중 연결 리스트의 O(1) 순서 변경을 합체!]

해시 테이블 배열 (단번에 위치 찾기 O(1))
  [버킷 0] ──> ...
  [버킷 1] ──> [노드: 아이폰] (해시로 1번에 찾음!)
                 ▲       ▼ (이 노드는 동시에 앞뒤 노드와 이중 연결 리스트로 묶여 있음!)
  순서 연결: [갤럭시] <─> [아이폰] <─> [맥북]  (앞뒤 고리만 풀어서 맨 끝으로 옮기면 O(1) 완료!)
```
* **원리**: 데이터들을 이중 연결 리스트로 줄 세워 순서를 유지하면서도, 각 노드를 해시 테이블(Hash Table)에 등록해 둔다. 덕분에 특정 데이터가 어디 있는지 **O(1)** 만에 즉시 찾아내고, 그 노드의 앞뒤 연결 고리만 바꿔서 맨 뒤로 보내거나 삭제하는 작업까지 **O(1)** 에 끝낸다.

```java
// 최근 접근한 순서(accessOrder = true)를 O(1)로 자동 유지하고 1,000개 초과 시 자동 삭제하는 캐시
Map<Long, Product> lruCache = new LinkedHashMap<>(1000, 0.75f, true) {
    @Override
    protected boolean removeEldestEntry(Map.Entry<Long, Product> eldest) {
        return size() > 1000; // 1,000개가 넘으면 가장 오래된 맨 앞 노드를 O(1)로 자동 삭제!
    }
};
```

* **면접 포인트**: 단순 선입선출(Queue)과 후입선출(Stack)에는 원형 배열 기반의 **`ArrayDeque`** 을 쓰고, 순서 유지와 함께 특정 요소의 중복 검사 및 위치 갱신이 **O(1)** 로 필요한 곳(LRU 캐시 등)에는 해시와 연결 리스트를 결합한 **`LinkedHashMap`** 을 선택하는 것이 백엔드 엔지니어링의 표준이다.

## 3. Deep Dive: 밑바닥 동작 원리와 연쇄 의문 해부

### 3-1. 왜 연결 리스트가 탄생했는가? (배열의 한계 돌파)
앞선 단원에서 배운 배열(Array)은 메모리에 빈틈없이 일렬로 배치되어 조회가 **O(1)** 이고 CPU 캐시 효율이 극강이지만, '연속성'을 유지하기 위해 두 가지 무거운 대가를 치렀다.
1. **거대한 연속 공간 확보의 어려움**: 100만 칸짜리 배열을 만들려면 RAM 어딘가에 100만 칸이 한 덩어리로 비어 있는 땅을 찾아야 한다.
2. **삽입·삭제와 크기 확장의 복사 비용**: 중간에 하나를 끼워 넣거나 뺄 때마다 뒤쪽 데이터를 전부 밀고 당기는 **O(N)** 메모리 복사가 강제된다.

연결 리스트는 **"데이터를 물리적으로 붙여 놓지 말고, RAM 빈자리 아무 데나 앉힌 뒤 '다음 사람의 메모리 번지(주소값)'만 들고 있게 하자"** 는 발상으로 이 제약을 돌파했다.

---

### 3-2. 노드(Node)의 물리적 메모리 구조와 24바이트 오버헤드 해부
연결 리스트는 실제 데이터만 저장하지 않고, 앞뒤 노드의 주소값을 함께 담는 **`Node` 객체** 단위로 힙(Heap) 메모리에 할당된다.

```java
// Java java.util.LinkedList 내부의 실제 Node 클래스 코드
private static class Node<E> {
    E item;         // 실제 데이터 객체를 가리키는 참조 주소 (4 Byte)
    Node<E> next;   // 다음 노드를 가리키는 참조 주소 (4 Byte)
    Node<E> prev;   // 이전 노드를 가리키는 참조 주소 (4 Byte)
}
```

```text
[1] 단일 연결 리스트 노드 (Singly Linked List Node)
+-------------------+-------------------+
|   item (참조 4B)   |   next (참조 4B)   | ──> 다음 노드의 메모리 번지
+-------------------+-------------------+

[2] 이중 연결 리스트 노드 (Java LinkedList 기준, 총 24 Byte 소모)
+-----------------------+-------------------+-------------------+-------------------+
| Object Header (12B)   |   prev (참조 4B)   |   item (참조 4B)   |   next (참조 4B)   |
+-----------------------+-------------------+-------------------+-------------------+
  ▲ JVM 객체 기본 이름표    ▲ 이전 노드 번지      ▲ 실제 데이터 번지    ▲ 다음 노드 번지
```

64비트 HotSpot JVM(Compressed OOPs 활성화 기준)에서 요소 1개를 관리하기 위해 쓰는 구조적 메모리를 비교하면 다음과 같다.
* **`ArrayList`**: 내부 배열 슬롯 1칸당 참조값 **4바이트** 만 소모한다.
* **`LinkedList`**: 노드 1개당 객체 헤더(12B) + `prev`(4B) + `item`(4B) + `next`(4B) = **24바이트** 를 소모한다(실제 데이터 객체 크기는 별도). 즉, 관리 비용만 `ArrayList` 의 **6배** 에 달한다.

---

### 3-3. 포인터 재배선(Pointer Rewiring)을 통한 O(1) 삽입·삭제와 포인터 체이싱(Pointer Chasing)

#### ① 포인터 재배선: 데이터 이동 없는 O(1) 삽입
이미 `Node A` 와 `Node B` 의 위치를 알고 있을 때, 그사이에 `Node X` 를 끼워 넣는 과정은 물리적인 데이터 복사 없이 **오직 4개의 주소값(포인터)만 갈아끼우는 작업** 으로 끝난다.

```text
[이중 연결 리스트에서 Node A와 Node B 사이에 새 Node X를 삽입하는 과정]

(삽입 전)
[Node A] ───────── next ─────────> [Node B]
[Node A] <──────── prev ───────── [Node B]

(삽입 후: 오직 4개의 화살표 방향만 수정! 뒤쪽 데이터 이동 0회 -> O(1))
               ┌──> [Node X] <──┐
          next │   prev   next  │ prev
               │    │      │    │
[Node A] ──────┘    ▼      ▼    └────── [Node B]
                 [Node A] [Node B]
```
1. `X.prev = A`, `X.next = B` 로 새 노드의 양팔을 먼저 연결한다.
2. `A.next = X`, `B.prev = X` 로 기존 앞뒤 노드의 고리를 새 노드로 향하게 바꾼다. 데이터가 1억 개여도 단 4번의 대입 연산(**O(1)**)이면 충분하다.

#### ② 포인터 체이싱(Pointer Chasing): CPU 캐시가 무력화되는 이유
연결 리스트의 노드들은 생성되는 시점마다 힙 메모리의 빈 공간 여기저기에 불규칙하게 흩어져 배치된다.

```text
[힙(Heap) 메모리에 파편화되어 흩어진 연결 리스트 노드들]

주소 0x1040: [Node 0 | next: @0x8920] ──┐
                                       │ (먼 메모리 번지로 점프!)
주소 0x3500: [Node 2 | next: @0x1200] <─┼──┐
                                       │  │ (또 다른 번지로 점프!)
주소 0x8920: [Node 1 | next: @0x3500] <─┘  │
                                          │
주소 0x1200: [Node 3 | next: null   ] <───┘
```
* CPU가 `Node 1` 이 어디 있는지 알기 위해서는 반드시 `Node 0` 을 메모리에서 먼저 읽어와 그 안의 `next` 주소(`0x8920`)를 열어봐야만 한다.
* 이처럼 꼬리에 꼬리를 물고 주소를 추적해야 하는 현상을 **포인터 체이싱(Pointer Chasing)** 이라 부른다. 다음 주소를 미리 알 수 없으므로 CPU의 **하드웨어 프리페처(Prefetcher, 미리 읽기 장치)가 작동하지 못하고**, 멀리 떨어진 메모리 번지로 점프할 때마다 캐시 미스(Cache Miss)가 빈번하게 발생한다.

### 3-4. 꼬리에 꼬리를 무는 의문 해결

#### 의문 1. "학부 자료구조 시간에는 분명히 연결 리스트가 삽입·삭제의 제왕이라고 배웠는데, 실무에서는 대체 언제 `LinkedList` 를 쓰는가? 아예 안 쓰는 건가?"
현업 Java 백엔드 개발에서 `java.util.LinkedList` 를 직접 생성해서 쓰는 일은 극히 드물다. 앞서 살펴본 것처럼 순차 조회는 `ArrayList` 가, 큐/스택은 `ArrayDeque` 이 메모리와 속도 모두 압승하기 때문이다.

하지만 **'연결 리스트라는 자료구조의 원리'** 자체는 실무 인프라와 프레임워크 밑바닥 곳곳에서 핵심 엔진으로맹활약하고 있다.
1. **`HashMap` 의 해시 충돌 해결 (Separate Chaining)**: 해시 테이블의 같은 버킷에 여러 데이터가 몰릴 때, 이 데이터들을 줄지어 매달아 두는 구조가 바로 단일 연결 리스트이다.
2. **`LinkedHashMap` 및 LRU 캐시 구현**: 캐시에서 가장 오래 안 쓴 데이터를 **O(1)** 에 밀어내고 방금 조회한 데이터를 맨 앞으로 옮길 때 이중 연결 리스트의 포인터 재배선 원리가 그대로 쓰인다.
3. **운영체제(OS)의 프로세스 스케줄링 큐 & 메모리 빈 공간 관리(Free List)**: OS 커널이 실행 대기 중인 프로세스 제어 블록(PCB)들을 줄 세우거나 쪼개진 메모리 블록들을 관리할 때 연결 리스트를 사용한다.
4. **직접 `LinkedList` 클래스가 유리한 예외적 상황**: 용량 예측이 전혀 불가능한 상태에서 배열 확장(`Resize`) 시 발생하는 일시적인 복사 지연(Latency Spike)조차 허용할 수 없거나, `ListIterator` 를 이용해 리스트 중간에서 앞뒤로 오가며 반복적으로 요소를 끼워 넣고 빼는 특수한 편집기 로직에서는 `LinkedList` 가 유리하다.

---

#### 의문 2. "단일 연결 리스트에서 특정 노드를 삭제할 때는 왜 노드를 알고 있어도 O(1)이 안 되고 O(N)이 걸리는가?"
삭제라는 작업의 본질이 **"내 앞 노드의 `next` 팔을 내 뒤 노드로 이어주는 것(`prevNode.next = targetNode.next`)"** 이기 때문이다.

```text
[단일 연결 리스트에서 Node B를 삭제하려 할 때의 딜레마]

[Node A] ─── next ───> [Node B (삭제 대상!)] ─── next ───> [Node C]
  ▲
  └── Node B는 자기 뒤에 Node C가 있다는 건 알지만(B.next),
      자기 등 뒤에 누가 서 있는지(Node A의 주소)는 알 방법이 없다! (prev 포인터가 없음)
```
* 단일 연결 리스트는 앞만 보고 서 있는 줄과 같다. 내가 `Node B` 를 손에 쥐고 있더라도, `Node A` 의 `next` 고리를 `Node C` 로 바꿔 걸어주려면 `Node A` 를 찾아야 한다.
* 하지만 뒤를 돌아볼 수 있는 `prev` 포인터가 없으므로, 결국 `Node A` 를 찾기 위해 맨 앞(`Head`)부터 `Node B` 직전까지 **O(N)** 으로 다시 걸어와야만 한다. 이것이 실무 라이브러리들이 메모리를 조금 더 쓰더라도 **이중 연결 리스트(Doubly Linked List)** 를 채택하는 결정적인 이유이다.

| 이렇게 단정하지 않기 | 이렇게 설명하기 |

## 4. 핵심 요약 및 기술 면접 대비 (한국 IT 기업 기준)

### ① 개발 과정을 이해하기 위해 챙겨야 할 감각
* **추상화 인터페이스(`List`, `Queue`) 뒤의 실제 구현체 의식하기**: 파라미터로 받은 `List` 에 습관적으로 `get(i)` 루프를 돌리면, 누군가 `LinkedList` 를 넘기는 순간 **O(N²)** 장애가 터진다. 순회는 항상 향상된 `for-each` 문을, 조건부 삭제는 `removeIf()` 를 쓰는 습관을 들여야 한다.
* **객체 할당(Allocation) 비용과 GC 감각**: 시간 복잡도가 같은 **O(1)** 이라도, 내부에서 `new Node()` 로 포장지 객체를 매번 찍어내는 `LinkedList` 와 기존 배열 슬롯만 재사용하는 `ArrayDeque` 은 대용량 트래픽 환경에서 큰 메모리 및 GC 성능 차이를 만든다.

### ② 면접 모범 답변 스크립트
> **"연결 리스트는 데이터를 연속된 메모리에 두지 않고, 힙 메모리에 흩어진 각 노드가 이전·다음 노드의 참조 주소값을 보유하여 논리적으로 연결된 자료구조입니다.**
> **배열과 달리 인덱스로 임의 접근이 불가능해 조회 시 O(N)이 소요되고 포인터 체이싱으로 인해 CPU 캐시 공간 지역성이 떨어진다는 단점이 있습니다. 또한 Java의 `LinkedList` 는 이중 연결 리스트로 구현되어 요소당 24바이트의 `Node` 객체 오버헤드가 발생합니다.**
> **반면 이미 노드의 위치를 알고 있는 `Iterator` 순회 중 삽입·삭제나 양 끝단 작업에서는 메모리 복사 없이 포인터만 변경하므로 진정한 O(1) 성능을 발휘합니다. 따라서 실무에서는 일반 목록 조회에는 `ArrayList` 를, 단순 큐·스택에는 원형 배열 기반의 `ArrayDeque` 을 사용하며, 순서 유지와 O(1) 탐색·삭제가 동시에 필요한 캐시 구조에서는 해시와 이중 연결 리스트를 결합한 `LinkedHashMap` 을 활용합니다."**
